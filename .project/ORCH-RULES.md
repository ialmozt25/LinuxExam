# ORCH-RULES.md — 9 правил оркестратора

## 1. Без spec — нет задачи

Каждая задача начинается со спеки `.project/specs/NNN-slug.md` (frontmatter +
разделы: Цель, Критерии приёмки, Что НЕ трогать, Превью). Нет спеки — задача не
берётся в работу, а сначала оформляется как `draft`, затем `preview`.

## 2. Approved spec = авторизация исполнения

**Approved spec = авторизация исполнения. Промежуточные approve не требуются.**
Коммит — только при зелёных гейтах (`typecheck`, `test:run`, `qc`, `sync:check`).

Капитан ставит `status: draft → approved`. Способ Фазы 2: ручная правка frontmatter
+ `npm run sync`. **Orchestrator НЕ переводит в `approved` сам.**

Что это меняет по сравнению с прежней редакцией («без approve капитана — нет коммита,
перед коммитом капитан видит preview»):

- капитан аппрувит **спеку**, а не каждый коммит. После approve оркестратор исполняет
  автономно: пишет код, прогоняет гейты, коммитит, обновляет производные;
- preview по-прежнему готовится и показывается — но как **отчёт о результате**, а не
  как запрос разрешения на коммит. Исключение — типы `content` и `ui`, где preview
  является частью приёмки (DOD: демонстрация артефакта до коммита);
- капитан видит результат в центре и откатывает через `git revert` (правило 8).

Границы, которые НЕ ослабляются:

- правило 4 (прод) в силе: `git push` — отдельный approve;
- правило 6 (freeze контента) в силе: content-спека не становится `approved` без
  разморозки;
- красный гейт отменяет коммит. «Автономно» не значит «несмотря на гейты».

## 3. Без зелёного sync:check — задача не done

Каноническая последовательность:

```powershell
npm run sync      # регенерировать производные из state.json
git add -A        # включить и state.json, и производные
git commit -m "..."   # один коммит
npm run sync:check    # exit 0 = done, exit 2 = SOURCE DRIFT
```

`sync:check` сравнивает сгенерированное с тем, что лежит в репозитории. Красный
гейт означает: производные (STATE.md / SPEC.md / docs/index.html) разошлись с
источником правды — сначала `npm run sync` и новый коммит, потом отчёт «done».

**Важно (изменено 2026-09-27, spec 009):**

- `sync:check` — **READ-ONLY**: ничего не пишет. Доказательство: hash `.project/state.json`
  до прогона равен hash после.
- `sync:check` **намеренно не** требует равенства `state.head == git HEAD`. Раньше это
  был гейт, и любой не-sync коммит (спека, отчёт, документ) делал проверку красной при
  полностью корректных производных — закрыть её можно было только ещё одним коммитом.
  За смену 2026-09-27 это стоило **5 лишних коммитов**. `state.head` теперь
  информационное поле: «состояние собрано на этом коммите».
- Самоссылочный участок центра (список последних коммитов) исключён из побайтового
  сравнения маркерами `<!--volatile:start-->` / `<!--volatile:end-->`: артефакт содержит
  отпечаток истории репозитория, в который его же и коммитят. Реальный дрейф при этом
  по-прежнему ловится (проверено: правка `STATE.md` → exit 2).

## 4. Прод https://ialmozt25.github.io/LinuxExam/ не трогать без approve

Прод — то, что видят пользователи. Любая задача, меняющая прод (сборка,
деплой, контент банка), требует явного approve капитана. При сомнении — не
делать и спросить. `git push` без approve запрещён.

## 5. Каждое решение — строка в .project/log.md (append-only)

Одно решение = одна строка `YYYY-MM-DD | milestone | что решено | commit <sha|pending>`.
Файл только дополняется: исправлять прошлые записи нельзя (история решений —
такой же источник правды, как `state.json`). Последние 10 строк видны в центре.

## 6. Контент-трек закрыт (freeze 2026-09-27)

Контент-трек закрыт. Content-спеки не создаются и не исполняются
без явного approve капитана. Разморозка — отдельным решением.

**Что это значит практически:**

- Банк заморожен на **206 вопросах**. Вопросы не добавляются, не удаляются
  и не правятся (включая правки текста, объяснений и порядка опций).
- Спеки `003` (глобальная канонизация опций) и `011` (дубль `tf_001`~`tf_002`)
  получили `status: rejected` — не «отложены», а отклонены в рамках freeze.
- Спеки `004`, `005`, `006` (батчи 5–7) закрыты как `done`: их вопросы
  закоммичены (`12c8439`).
- Открытыми остаются только **инфраструктурные** спеки: `007` (семантика ratio
  в `tools/qc.cjs`), `008` (роль DevOps документом), `010` (jsdom smoke-тесты
  центра). Они не создают и не меняют контент банка — их исполнение freeze
  не блокирует. (`009` закрыта 2026-09-27: `--check` стал READ-ONLY и перестал
  быть гейтом равенства `head == HEAD`; см. правило 3.)
- Найденные, но не исправленные аномалии банка (`tf_001`~`tf_002` cos 0.9020,
  `ms_002`~`ms_008` 0.8527, дубли верной опции `ug_002`~`ug_018` и
  `ds_013`~`pm_014`, четыре объяснения, спорящие с содержанием) остаются
  зафиксированными в `.project/audits/bank-audit-2026-09-27.md` и `docs/HANDOFF.md`
  §7.4 — как открытый долг, а не как забытые находки.
- Следующий трек — **MAS фабрика**. Разморозка контента — по решению капитана.

## 7. Центр — единственный интерфейс капитана

**Вступает в силу ПОСЛЕ Фазы 2.** Сама Фаза 2 approve-ится в чате — последний раз.

- Капитан смотрит состояние в центре `docs/index.html`: Done / Doing / Next, очередь
  решений, спеки, коммиты, роли, продукты, аудит, память, политики.
- Центр — **только показ**. Он не управляет: ни кнопок, ни approve, ни запуска ролей.
  Решение капитана идёт через `status` спеки (правило 2).
- Всё в центре генерируется (`npm run sync`) из `state.json`, `git log`,
  `.project/specs/*.md` и `.project/factory/roles.yaml`. Ручная правка `docs/index.html`
  затирается следующим `sync` — и это правильно.
- Спецификация центра: `.project/factory/CENTER-SPEC.md`.

## 8. Откат — git revert + запись в log.md

**Откат — `git revert <SHA>` + запись в `.project/log.md`.** Orchestrator не откатывает
по своей инициативе.

- Откатывает **капитан**: он видит результат в центре и решает. Автономность
  (правило 2) распространяется на исполнение, но не на отмену уже принятого.
- Откат — новый коммит (`git revert`), а не перезапись истории: `log.md` и `DECISIONS.md`
  append-only, и отменённое решение должно остаться видимым.
- Запись в `log.md` обязательна: `YYYY-MM-DD | rollback | что откатили и почему | commit <sha>`.
- Если откат затрагивает контент банка — он возможен только при разморозке (правило 6).

## 9. Конвергентный коммит — постоянная стоимость state

**Конвергентный коммит.** Завершение задачи включает **+1 коммит**
`chore(state): converge after <task>` для синхронизации `state.json` и производных.
Это **постоянная стоимость** самоссылочного state, **не дефект**.

**Правило 3 (уточнение):** задача `done` = после конвергентного коммита
`sync:check` = **exit 0**. Конвергентный коммит — **часть завершения**, не нарушение.

- **Не пытаться устранить.** Самоссылочность `commits[]` в `state.json`
  (артефакт содержит отпечаток истории, в которую его же и коммитят) принята как данность.
- **Не создавать спек на фикс.** Тема закрыта: spec `012` → `rejected`
  (2026-09-27, time-box exceeded). Три попытки (D6, D3, `012`) = 400+ минут без результата.
- Практика: `npm run sync` → коммит задачи → коммит `chore(state): converge after <task>`
  → `npm run sync:check` = exit 0 → push.
