# ORCH-RULES.md — 5 правил оркестратора

## 1. Без spec — нет задачи

Каждая задача начинается со спеки `.project/specs/NNN-slug.md` (frontmatter +
разделы: Цель, Критерии приёмки, Что НЕ трогать, Превью). Нет спеки — задача не
берётся в работу, а сначала оформляется как `draft`, затем `preview`.

## 2. Без approve капитана — нет коммита

Перед коммитом капитан видит preview (что именно изменится, где посмотреть) и
**решение принимает он**. Никаких «сделал, потому что очевидно»: спека в статусе
`preview` ждёт капитана в «Очереди решений» центра. Push в прод — отдельный
approve (правило 4).

## 3. Без зелёного sync:check — задача не done

Каноническая последовательность:

```powershell
npm run sync      # регенерировать производные из state.json
git add -A        # включить и state.json, и производные
git commit -m "..."   # один коммит
npm run sync:check    # exit 0 = done, exit 2 = SOURCE DRIFT
```

`sync:check` сравнивает сгенерированное с тем, что лежит в репозитории. Красный
гейт означает: производные (STATE.md / SPEC.md / docs/index.html) разошлись с
источником правды — сначала `npm run sync` и новый коммит, потом отчёт «done».

## 4. Прод https://ialmozt25.github.io/LinuxExam/ не трогать без approve

Прод — то, что видят пользователи. Любая задача, меняющая прод (сборка,
деплой, контент банка), требует явного approve капитана. При сомнении — не
делать и спросить. `git push` без approve запрещён.

## 5. Каждое решение — строка в .project/log.md (append-only)

Одно решение = одна строка `YYYY-MM-DD | milestone | что решено | commit <sha|pending>`.
Файл только дополняется: исправлять прошлые записи нельзя (история решений —
такой же источник правды, как `state.json`). Последние 10 строк видны в центре.
