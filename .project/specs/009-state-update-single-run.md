## ⚠️ Сужение области (2026-09-27, M6.0 Phase 2, D6)

**Закрыт только один класс дефекта из этой спеки — дрейф `sync:check`.**
Остальные критерии ниже (единый вход, однократный прогон гейтов, честный exit-код
`state:update`, решение по `docs/dashboard/state.json`) **не выполнены** и выносятся
в отдельную спеку. Отмечаю это явно, чтобы `status: done` не создавал ложного
впечатления закрытой темы.

**Что сделано (commit `d61112d`):**

- `--check` доказанно READ-ONLY: hash `state.json` до прогона = после. Ветка проверки
  возвращает управление до любой записи.
- Снят **гейт равенства** `state.head == git HEAD`. Это и был источник «вечного»
  convergence-коммита: любой не-sync коммит (спека, отчёт, документ) двигал HEAD,
  гейт краснел при полностью корректных производных, а закрыть его можно было лишь
  ещё одним коммитом — потому что `head` пишется только в ветке записи. За смену
  2026-09-27 это стоило **5 лишних коммитов**.
- `state.head` переведён в **информационное** поле («состояние собрано на этом
  коммите»). Закрепление HEAD сохранено: без него производные перестают быть
  байтово стабильными и `--check` краснеет всегда (проверено — промежуточная версия
  правки ломала стабильность).
- Добавлена проверка `schema_version < 2` в `--check`.

**Замеренные доказательства:**

| Проверка | Результат |
|---|---|
| `sync:check` сразу после sync-коммита, HEAD ушёл вперёд | **exit 0**, без доп. коммита |
| не-sync коммит → `sync:check` | **exit 2** (дрейф производных), `state.json` hash не изменился (**True**) |
| `npm run sync` дважды подряд | второй прогон: `записано файлов: 0`, state.json идемпотентен |

**Исправление ошибочного утверждения.** `tools-audit-2026-09-27.md` (раздел C.5)
утверждал, что `npm run sync:check` перезаписывает `.project/state.json`. Проверено
эмпирически дважды: **это неверно**, ранний `return` в ветке проверки существовал
до правки. Реальная причина лишних коммитов — гейт равенства `head == HEAD`.
Аудит подлежит правке отдельно.

## Цель

Один вход, который прогоняет гейты, обновляет `.project/state.json` и пересобирает
производные, без второго прогона гейтов и без ловушки «незакоммиченные производные».
Сейчас после каждой задачи нужно помнить про два шага в правильном порядке, а гейт
`sync:check` (DOD/ORCH-RULES, правило 3) требует ещё и третьего — коммита между ними.

## Фактический поток сегодня (проверено чтением кода)

1. `npm run state:update` → `tools/gen-state.mjs` (`package.json:15`).
   - Прогоняет **четыре** гейта как npm-скрипты: `qc`, `typecheck`, `test:run`,
     `shuffle-bank:check` (`tools/gen-state.mjs:419-455`); `--no-gates` переиспользует
     прошлые значения (`:503-511`).
   - Пишет `.project/state.json` (`:537-539`, LF, без BOM, последний байт `0x0A`).
   - **Побочный эффект:** безусловно копирует его в `docs/dashboard/state.json`
     (`:545-549`, `fs.copyFileSync`) — легаси-дашборд V1–V9.
   - В шапке-документации (`:7-18`) этот побочный эффект **не** перечислен.
   - Завершается **exit 0 даже при красных гейтах**: `process.exitCode` ставится только
     в `catch` (`:598-607`).
2. `npm run sync` → `.project/sync.mjs` (`package.json:16`) — читает `state.json`,
   `PLAN.md`, `specs/*.md`, `log.md`, `_topics.json` и пишет три производных:
   `.project/STATE.md`, `.project/SPEC.md`, `docs/index.html`
   (`.project/sync.mjs:56-58`, `:752-756`); `last_sync` идемпотентен (`:739-744`).
3. `npm run sync:check` → тот же файл с `--check` (`:762-801`): сверяет производные
   побайтово с источником, проверяет `head` против якоря, требует наличия ключей
   `head/specs/log_tail/last_sync` и **требует, чтобы четыре пути были закоммичены**
   (`:785-788`); при расхождении — exit **2**.

**Реальные отказы этого потока:**

- **Двойной прогон.** Любой скрипт, который хочет «и гейты, и производные», вынужден
  вызывать оба шага; `qc`/`typecheck`/`test:run` при этом исполняются повторно, если
  задачу закрывают двумя командами.
- **Порядок и окно.** `sync` нужно запускать после `state:update` и **до** коммита,
  а `sync:check` — **после** коммита (`diffHead` сравнивает HEAD ↔ дерево,
  `.project/sync.mjs:174-182`). Забытый шаг даёт либо устаревшие производные, либо
  красный exit 2: в аудите `.project/audits/tools-audit-2026-09-27.md` (C.3) зафиксирован
  именно такой случай — `sync:check` = exit 2 после не-sync-коммита.
- **Скрытый пятый файл.** `docs/dashboard/state.json` перезаписывается каждым
  `state:update`, хотя DECISIONS 2026-09-27 (п. 7) требует его не коммитить, а
  `sync:check` его не мониторит (там же: гейт смотрит только четыре пути). Итог —
  «грязный» файл, который либо случайно уезжает в коммит, либо мешает читать
  `git status`.
- **Молчаливо зелёный красный гейт.** `state:update` возвращает 0 при `Fails > 0`
  в `qc` (audit, B.5, позиция 6) — в автоматизации это неотличимо от успеха.

## Критерии приёмки

- [ ] Один документированный вход (npm-скрипт) выполняет всё: гейты → `state.json` →
      `.project/STATE.md` + `.project/SPEC.md` + `docs/index.html`. Имя входа
      зафиксировано в `package.json` и упомянуто в отчёте; существующие
      `npm run state:update`, `npm run sync` и `npm run sync:check` продолжают работать
      как раньше (их семантика не ломается).
- [ ] Гейты в этом входе исполняются **ровно один раз**: `qc`, `typecheck`, `test:run`,
      `shuffle-bank:check` — по одному запуску; доказательство в превью (вывод каждого
      гейта ровно один раз + `gates.*.last_run` совпадает у всех четырёх гейтов в
      обновлённом `state.json`).
- [ ] Повторный запуск входа на неизменённом дереве не даёт новых изменений, кроме
      timestamp-полей (`state.json.last_update`, `state.json.last_sync`,
      `gates.*.last_run`); `docs/index.html`, `SPEC.md`, `STATE.md` при этом байтово
      не меняются (идемпотентность, уже обеспеченная `.project/sync.mjs:739-744`).
- [ ] Непустой exit-код при красном гейте: если любой из четырёх гейтов вернул non-zero,
      вход завершается non-zero (сейчас `tools/gen-state.mjs:533-539` этого не делает).
      Осознанное решение: включить это в скоуп, потому что «зелёный при красных гейтах»
      делает единый вход бессмысленным. `--no-gates` не меняет поведение.
- [x] `sync:check` сохраняет семантику: exit 0 — производные совпадают с источником,
      exit 2 — дрейф; exit-код и текст сообщений не переформулируются.
      **Выполнено** — см. «Что сделано» выше.
- [ ] **Решение по `docs/dashboard/state.json` зафиксировано явно** — либо
      (а) копирование остаётся, но перечислено в шапке `tools/gen-state.mjs:7-18` как
      записываемый артефакт и внесено в `.gitignore` (или иначе исключено из коммита),
      либо (б) копирование удалено как легаси-артефакт. Выбор аргументирован в отчёте
      (влияние на `docs/dashboard/*`, BACKLOG, риск случайного коммита).
- [ ] `git status --porcelain` сразу после запуска входа показывает **только**
      ожидаемые пути: `.project/state.json`, `.project/STATE.md`, `.project/SPEC.md`,
      `docs/index.html` (+ `docs/dashboard/state.json`, только если выбран вариант (а)
      с leave-as-is — тогда он обязан быть в `.gitignore` или возвращён к HEAD).
      Список путей приведён в превью дословно.
- [x] После `git add` + одного коммита: `npm run sync:check` exit 0.
      **Выполнено** — и более того, **без** дополнительного convergence-коммита.
- [x] `npm run typecheck` exit 0, `npm run test:run` exit 0, `npm run build` exit 0.
- [ ] Строка в `.project/log.md` (append-only) и запись в `.project/DECISIONS.md`,
      если решение по легаси-дашборду меняет ранее принятое (DECISIONS 2026-09-27, п. 7).

## Превью

1. Точный список команд входа и вывод одного полного прогона (с видимым однократным
   запуском каждого гейта).
2. `git status --porcelain` сразу после прогона — дословно.
3. Diff `package.json` (новое имя входа) и `tools/gen-state.mjs` (exit-код, шапка,
   решение по `docs/dashboard/state.json`).
4. Доказательство идемпотентности: второй прогон подряд и его `git status`.
5. Подтверждение, что `npm run sync` и `npm run sync:check` работают по-старому
   (вывод `sync:check` exit 0 после коммита).
