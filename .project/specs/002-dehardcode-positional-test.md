## Цель

Убрать хардкод ожидаемого размера банка из guard-теста
`src/data/questions/__tests__/positional-distribution.test.ts`, из-за которого
каждый новый батч вопросов требует ручной правки теста (`EXPECTED_QUESTIONS`
183 → 189 в M2.9 batch 4 — commit этой же сессии). После задачи тест должен
читать ожидаемое число вопросов из источника истины (`.project/state.json`
и/или `src/data/questions/_topics.json`), а не из константы в коде.

Возникло как tech debt M2.9 batch 4: spec 001 запрещал трогать
`src/data/questions/*`, но без правки константы гейт `npm run test:run` падал.
Капитан разрешил разовую правку 183 → 189 и потребовал отдельную спеку.

## Триггер запуска

**Сразу после approve batch 4, до batch 5.** Иначе следующий батч снова
потребует ручной правки константы.

## Отклонения

Зафиксировано по итогам выполнения (2026-09-27):

- **Источник вместо `.project/state.json`.** Спека допускала выбор из двух
  источников. Выбран `_topics.json` (слой данных), а не
  `.project/state.json`. Причина: `state.json` лежит вне `tsconfig.app.json`
  (`include: ["src"]`), читается инструментами координации и **уже** содержит
  `goal.current_questions`, который заполняется из `_topics.json` при
  `npm run state:update`. То есть тест с чтением `state.json` дублировал бы
  связь, которую уже держит инструментарий, и зависел бы от каталога,
  не входящего в сборку. `_topics.json` — ровно «данные банка» из формулировки
  спеки, и он же источник `getBankTotal()`, которым пользуется приложение.
- **Наивная негативная проверка из плана ночи не сработала бы.** План предлагал
  «`state.json.current_questions` +1 → тест падает». При выбранном источнике
  тест читает `_topics.json`, поэтому правка `state.json` тест не роняет — и это
  правильно: `state.json` перезаписывается `npm run state:update`, то есть
  временная правка молча затирается и доказательство недостоверно. Вместо неё
  выполнен стресс-тест на самом источнике (`_topics.json`) плюс проверка на
  копии банка; оба дали ожидаемый красный/зелёный. Разбор — в DECISIONS.md.
- **Правка frontmatter'а — отдельным коммитом (`chore(spec)`, упрощённый
  lifecycle).** Раздел «Критерии» плана требовал `done` + SHA в том же коммите,
  что и задача. SHA коммита не существует до его создания, а правка файла
  меняет его содержимое, поэтому SHA указывает на коммит **кода** `cd6ce8d`;
  статус и SHA зафиксированы следующим коммитом. Раздел README «Lifecycle»
  (коммит `1a4950b` этой же смены) явно разрешает упрощённый путь для мелких
  задач. Одним коммитом `done` + верный SHA недостижимы без переписывания
  истории.
