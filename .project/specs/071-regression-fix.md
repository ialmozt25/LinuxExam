### P1 — next-button

| | Факт |
|---|---|
| Симптом | кнопка ниже фолда, нужен скролл (только на устройстве) |
| Воспроизведение в Playwright | **НЕТ** |
| Воспроизведение в TMA-эмуляции | **НЕТ** (эмуляция не даёт нативный MainButton; см. ниже) |
| Причина | **не подтверждена** |

Замеры (390×844, вопрос `et_018` с самым длинным объяснением):

- `footer.position = fixed`, `zIndex = 50`, топ 755 / низ 844 при `innerHeight 844`;
- `next-button`: топ 780 / низ 836, `disabled = false`, `toBeInViewport({ratio:1})`;
- цепочка родителей футера (`div → div → #root → body → html`): **ни одного**
  `transform` / `will-change` / `filter` / `perspective` / `contain` —
  содержащий блок для `fixed` не создаётся (это была основная гипотеза задания);
- прокрутка в самый низ (`scrollTop 660`) позицию футера **не меняет**
  (780/836 → 780/836).

В TMA-ветке (`isTMA() === true`) in-app футер и распорка **не рендерятся вообще**
(`next-button: 0`, `fixed-footer-spacer: 0`) — роль кнопки берёт нативный
MainButton Telegram. Это значит: **на устройстве P1 зависит от нативной кнопки
Telegram, а не от CSS `fixed`-футера spec 070.** Эмулировать нативную кнопку
Playwright не может — её поведение задаёт сам клиент Telegram.

Не подтверждённые, но проверяемые на устройстве гипотезы (для эскалации):

1. Приложение на устройстве открыто **не как Mini App** (`isTMA() === false`) —
   тогда рендерится in-app футер, а он и есть «невидимая» кнопка;
2. `visualViewport.height` в WebView больше фактически видимой области —
   тогда `fixed; bottom: 0` отсчитывается от вьюпорта, который ниже края экрана
   (это ровно тот класс дефекта, который spec 067/070 пытались закрыть, и он
   **не моделируется** `setViewportSize`: в Playwright layout и visual viewport
   меняются синхронно);
3. Нативная MainButton не показывается из-за состояния SDK/платформы.

## Что делаем

### F1 (P1) — причина не подтверждена → эскалация (не угадывать)

Задание прямо перечисляет только два исхода для F1: (A) transform/will-change на
`#root` → вынести анимацию / `createPortal`; (B) причины в computedStyle нет →
**эскалация**. Измерения дали ровно (B): содержащих блок свойств нет, кнопка
в вьюпорте, прокрутка позицию не меняет. Слепой фикс (`createPortal`,
`dvh`-переделка `#root`) менял бы поведение **без подтверждённой причины** и не
проверялся бы ничем, кроме ручного теста на устройстве, — это прямо запрещено
условием задачи и правилом «не фиксить, пока причина не подтверждена».

Вместо фикса сделано то, что проверяемо детерминированно: регрессионный тест,
который поймает **любое** появление содержащего блока и потерю видимости кнопки
(см. F4), плюс зафиксирован факт «в TMA-ветке in-app футера нет вообще».

### F2 (P2) — причина не подтверждена → эскалация

Воспроизведения нет ни в основном сценарии, ни в полном прогоне 30/30, ни с
`pageerror`-хуком. Фикс «на всякий случай» менять нечего: конкретной ошибки нет.

### F3 (P3) — причина не подтверждена → эскалация

То же: экран рендерится, ошибок нет, данные домена не тронуты. Единственная
наблюдаемая странность (нули в «Слабых темах» на пустом профиле) — вне
write-скоупа и требует решения капитана, а не автофикса.

Лимит «2 попытки фикса» не израсходован: попыток фикса нет, потому что нет
подтверждённой причины. Правило задания соблюдено буквально.

### F4 — регрессионные тесты: `e2e/regression-071.spec.ts`

Четыре теста, все с `pageerror` + `console.error` (шум dev-сервера и `net::ERR_*`
отфильтрованы — иначе проверка «errors=0» красная всегда):

1. **P1** (390×844, вопрос `et_018`): после ответа `next-button`
   `toBeInViewport({ratio:1})`, низ кнопки ≤ `innerHeight`, футер `fixed`/`zIndex 50`,
   **цепочка родителей футера не содержит** `transform` / `will-change` / `filter` /
   `perspective` / `contain`, и позиция кнопки не меняется при прокрутке в самый низ;
2. **P2**: `exam-mode` → `exam-setup` («Вопросов в прогоне: 30») → `exam-start` →
   3 вопроса с проверкой `exam-progress` → `exam-cancel` целиком в вьюпорте;
3. **P3**: `analytics-mode` → экран, `analytics-empty` виден, readiness/radar

**Статус тестов — характеризующий, не доказывающий.** Они фиксируют наблюдаемое
поведение и ловят регрессию; «тест зелёный» **не означает** «на устройстве
работает». Прямая формулировка из задания: не писать «тест зелёный = работает».

1. **Какая именно сборка на устройстве.** Пуш `6eb3bdd..bbd25c0` (spec 070)

2. **P1 — включён ли Mini App-режим.** В Telegram WebView выполнить в консоли
   DevTools (Telegram Desktop → «…» → Open DevTools, либо `chrome://inspect`):

   ```js
   ({
     tma: !!window.Telegram?.WebApp,
     platform: window.Telegram?.WebApp?.platform,
     innerHeight: window.innerHeight,
     vvHeight: window.visualViewport?.height,
     vvOffsetTop: window.visualViewport?.offsetTop,
     appHeight: getComputedStyle(document.documentElement).getPropertyValue('--app-height'),
     rootBottom: document.getElementById('root')?.getBoundingClientRect().bottom,
     devBadge: document.body.innerText.match(/TG: |Web mode/)?.[0] ?? null,
   })
   ```

   Ключевое: `tma: false` означает, что приложение открыто как обычный браузер
   внутри WebView — тогда работают in-app футер и `fixed`, а не MainButton.
3. **P2 — что именно значит «не грузится»**: «Экзамен не запущен»

   подтверждено тестом.

   поведение `visualViewport` в WebView различается, и это единственный
   непроверяемый здесь фактор.
