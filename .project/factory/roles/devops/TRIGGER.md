# TRIGGER.md — триггер роли DevOps

**M6.0 Phase 4 (D3) · 2026-09-28.** Машинночитаемая часть — та же, что в
`.project/factory/roles.yaml` (источник истины по составу ролей). Здесь — состояние
триггера и объяснение, **почему** он считается сработавшим.

```yaml
role: devops
trigger:
  human: "deploy failed 3+"
  check: null            # машинного условия нет: триггер РУЧНОЙ
fired: true
fired_at: 2026-09-28
fired_by: "Капитан (M6.0 Phase 4)"
status_after: active
preset: null             # preset pending: пресет роли не создан
```

## `check: null` — это не «забыли заполнить»

`null` означает «триггер ручной»: центр обязан пометить роль как ручную, а не
изобретать псевдо-условие ради заполненности поля (`roles.yaml`, «Правила заполнения»).
У DevOps условия в наблюдаемых метриках нет: «3+ упавших деплоя» — событие в GitHub
Actions, которое никто не считает автоматически, поэтому решение принимает капитан.

## Почему `fired: true`

- Капитан **авторизовал** роль в M6.0 Phase 4: `roles.yaml` — `devops: planned → active`,
  `preset: null` (пресет не создаётся, статус — `preset pending`).
- Интерпретация триггера `"deploy failed 3+"` в этой фазе: **«пилот завершён»**.
  Фаза 3 довела инфраструктурный трек до состояния, когда у роли появилась работа
  (гейты перед релизом, гигиена `deploy.yml`, зависимости — см. `docs/HANDOFF.md` §7),
  и роль перестала быть гипотетической. Это решение капитана, а не измеренное условие.
- Роль существует **как документ** (`docs/knowledge/ops/devops-role.md`, spec 008) и
  артефактами в этом каталоге; пресет не создаётся, пока не сработает триггер эскалации.

## Что НЕ означает `fired: true`

- Это **не** разрешение на push в прод: правило 4 ORCH-RULES в силе, `git push` —
  отдельный approve капитана.
- Это **не** создание пресета: `preset: null` остаётся. Эскалация до пресета — отдельное
  решение капитана (условия — `docs/knowledge/ops/devops-role.md`, «Триггеры эскалации»).
- Это **не** расширение скоупа: роль по-прежнему не трогает контент банка (правило 6)
  и не правит `src/**` без спеки.

## Как вернуть роль в `planned`

Только решением капитана: `roles.yaml` — `status: planned`, `fired: false` здесь,
`note` без «preset pending». Причина откатов, требующая записи: роль так и не получила
нагрузки (сработала бы проверка «пресет без нагрузки — стоимость без отдачи»).
