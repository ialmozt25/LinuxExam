# CENTER-SPEC.md — спецификация центра разработки (вид на всю работу фабрики)

**M6.0 Phase 1 · дата: 2026-09-27 · автор: Orchestrator · статус: дизайн, НЕ внедрено**

Спецификация центра как **единого вида на всю работу фабрики**: продукты, спеки, роли,
коммиты, память, аудиты. Реализация — Фаза 2 (расширение `.project/sync.mjs`).
Здесь определён **контракт данных и разделов**, а не код.

- База: HEAD `92d3bcd`, банк **206 (заморожен)**, ORCH-RULES правила 1–6.
- Смежные документы: `ARCHITECTURE.md` (слои и роли), `DOD.md` (критерии), `CONTRACTS.md`.

---

## 0. Принцип: всё генерируется, руками не правится

Центр — **производный артефакт**. Ни один его байт не пишется человеком. Источники:

| Источник | Что даёт | Статус |
|---|---|---|
| `.project/state.json` | агрегаты: прогресс, спеки, темы, гейты, коммиты | **есть**, расширяется (§9) |
| `git log` / `git rev-parse` | HEAD, история коммитов, даты | **есть** |
| `.project/specs/*.md` | frontmatter спеков + секции | **есть** |
| `roles.yaml` | состав ролей, статусы, триггеры | **новый файл**, §8 |
| `.project/log.md` | журнал решений (append-only) | **есть** |
| `.project/audits/*`, `.project/factory/*` | отчёты и research | **есть** |
| `.project/PLAN.md`, `DOD.md`, `ORCH-RULES.md`, `TOKENS.md` | политики | **есть** |

**Правило:** если раздел невозможно вывести из этих источников — он либо не попадает
в центр, либо для него сначала заводится источник. Раздел, который «приходится
обновлять руками», запрещён: именно так в проекте сгнили `STATE.md` и старый дашборд
(M4.0, DECISIONS).

## 2. Разделы центра

Порядок разделов — это **приоритет для капитана**: сверху то, что требует его решения.

### 2.1 Шапка

| Поле | Источник | Формат |
|---|---|---|
| HEAD | `git rev-parse --short HEAD` | `92d3bcd` |
| last_sync | `state.json.last_sync` | ISO-8601 UTC |
| статус sync | результат `sync.mjs --check` | 🟢 синхронизировано / 🔴 расхождение |
| активная сессия | `.dsh`/session log — **источник не определён**, см. §10 Q1 | «—» если нет |
| продукты (кратко) | `state.json.products[]` | `LinuxExam 206/300 · frozen` |

**Отличие от текущего:** сейчас шапка показывает статус sync **всегда зелёным**
(генератор вызывает себя в режиме записи и по определению «в синхроне»). Это
**дефект**: честный статус требует прогона `--check`. В Фазе 2 шапка получает
реальный результат проверки (это же закрывает находку аудита: `--check` валидирует
только наличие ключей).

### 2.2 Очередь решений (главный блок, сверху)

**Источник:** `state.json.specs[]`, фильтр `status === 'preview'`.
**Пусто →** строка «Решений не ждёт».

На одну спеку: `id`, `slug`, `type`, цель (первая непустая строка секции `## Цель`),
путь к спеке.

**Почему сверху:** правило 2 (без approve капитана — нет коммита). Очередь — это
единственный блок, который может **изменить поведение фабрики**; остальное — наблюдение.

**Текущее состояние:** очередь пуста (все спеки либо `done`, либо `rejected`, либо
`draft`). Это нормально для замороженного контент-трека, но значит, что блок надо
проверить на непустом примере до сдачи Фазы 2.

### 2.3 Активная работа

| Поле | Источник | Формат |
|---|---|---|
| Роль | `roles.yaml` + `state.json.active_tasks[]` | `Orchestrator` / `Writer` / `QC` / … |
| Спека | `active_tasks[].spec_id` | `010-jsdom-smoke-center` |
| Что делает | `active_tasks[].summary` | одна строка |
| Время старта | `active_tasks[].started_at` | ISO-8601, локальное время |

**Проблема, которую надо решить в Фазе 2 (честно):** «кто работает прямо сейчас» —
**не выводится из git**. Коммит появляется только в конце. Варианты источника,
в порядке предпочтения:

1. **Файл-сердцебиение** `.project/factory/active/<role>.json`, который агент
   перезаписывает при старте и завершении задачи. Минус: агент может не успеть
   записать (падение) → устаревшая метка. Митигация: поле `started_at` + порог
   «старше N часов → показать как `stale`».
2. **Последний артефакт роли по mtime** (`.project/drafts/*writer-output*`,
   `.project/agents/*report*`). Полностью выводимо, но даёт «последняя активность»,
   а не «работает сейчас».
3. **Не показывать вовсе.** Пока `state.json.active_tasks` пуст, раздел показывает «—».

**Решение для Фазы 2:** вариант 1 как основной, вариант 2 как fallback при отсутствии
файла. Вариант 3 — текущее поведение по умолчанию. См. §10 Q1.

### 2.4 Все спеки

**Источник:** `state.json.specs[]`.

| Колонка | Источник |
|---|---|
| id | frontmatter `id` |
| slug | frontmatter `slug` |
| type | frontmatter `type` |
| status | frontmatter `status` |
| **role** | **`roles.yaml` — кто исполняет этот `type`** (новое) |
| commit | frontmatter `commit` |
| updated | frontmatter `updated` |

**Сортировка:** `preview → running → approved → draft → done → rejected`
(уже реализована в `sync.mjs`, `STATUS_ORDER`).

**Новая колонка `role`.** Маппинг `type → role` берётся из `roles.yaml`
(§8), а не из спеки: спека не должна знать, кто её исполняет — иначе смена роли
потребует правки каждой спеки.

| type | role |
|---|---|
| `content` | `content-writer` |
| `ui` | `designer` |
| `feature` | `orchestrator` |
| `infra` | `devops` (или `orchestrator` — см. §10 Q2) |
| `docs` | `orchestrator` |

### 2.5 Коммиты (последние 20)

**Источник:** `git log -20 --pretty=format:%h%x09%ad%x09%s --date=short`.

| Колонка | Источник |
|---|---|
| SHA | `%h` (7 символов) |
| message | `%s` |
| дата | `%ad` (`--date=short`) |
| тип | **выводится из message**: `^(feat|fix|docs|chore|refactor|test|style|perf|build|ci)\b` |

**Детали, которые надо учесть:**

- **Тип выводится из префикса**, а не хранится. Коммит без conventional-префикса
  показывается как `—`, и это **сигнал**: значит, коммит сделан вне правил.
- **Кодировка:** сообщения содержат кириллицу; вывод `git` читается как UTF-8.
  `sync.mjs` уже решает это через `execFileSync(..., {encoding:'utf8'})`.
- **20 коммитов, а не 5.** Сейчас `state.json.recent_commits` хранит 5 (для дашборда).
  Для раздела 20 берётся напрямую из `git log` (дешевле, чем расширять `state.json`).
- **Часовой пояс:** `git log` отдаёт дату автора в его поясе (`+1000` здесь).
  Не нормализовать — капитан должен видеть свои локальные даты.

### 2.6 Роли

**Источник:** `roles.yaml` (§8).

| Колонка | `roles.yaml` ключ |
|---|---|
| роль | `name` |
| статус | `status` (`active` / `planned` / `deferred`) |
| триггер запуска | `trigger` |

Начальные значения по заданию:

| роль | статус | триггер |
|---|---|---|
| Orchestrator | `active` | старт сессии |
| Writer (content-writer) | `active` | спека `content` в `running` |
| QC (qc-auditor) | `active` | Writer вернул DONE/PARTIAL |
| DevOps | `planned` | **после пилота** |
| Designer | `planned` | **вторая UI-задача** |
| Test | `planned` | рост тестов (см. §10 Q3) |

**Замечание по триггерам:** «после пилота» и «рост тестов» — **непроверяемые**
формулировки. В `roles.yaml` триггер описывается в двух полях: `trigger.human`
(человеческое описание) и `trigger.check` (машинночитаемое условие). Если `check`
не выражается — триггер считается **ручным** и помечается явно. Иначе раздел
превратится в документацию пожеланий.

### 2.7 Продукты

**Источник:** `state.json.products[]` (новое, §9).

| Колонка | Ключ |
|---|---|
| продукт | `name` |
| статус | `status` (`active` / `frozen` / `planned`) |
| метрика | `metric` (текст: «206 / 300 вопросов») |
| freeze/unfreeze | `frozen_at` (дата) + ссылка на правило/спеку |

Начальные значения:

| продукт | статус | метрика | freeze |
|---|---|---|---|
| LinuxExam | `frozen` | банк 206 / 300, 14 тем | 2026-09-27, ORCH-RULES правило 6 |
| `<next>` | `planned` | — | — |

**Почему продукты вынесены отдельно от прогресса банка:** фабрика заявляет
мультипродуктовость (ARCHITECTURE §1 слой 5). Пока продукт один, это выглядит
избыточным, но именно здесь фиксируется переход: прогресс банка становится
**метрикой одного из продуктов**, а не сущностью центра.

**Метрика не дублирует `goal`:** `products[].metric` — строка для отображения,
рассчитанная из `state.json.goal`. Дублирования данных нет, есть ссылка
(`metric_source: 'goal'`).

## 3. Технические требования

| # | Требование | Как проверяется |
|---|---|---|
| Т1 | Один HTML-файл `docs/index.html` | `git ls-files docs/index.html` |
| Т2 | Инлайн CSS, без внешних ресурсов | нет `<link rel="stylesheet">`, нет `<script src>` |
| Т3 | Без фреймворков, без билда | нет `node_modules` в зависимостях страницы |
| Т4 | Без кнопок (пока) | нет `<button>`, нет обработчиков |
| Т5 | Генерируется `sync.mjs` | `sync:check` ловит ручную правку |
| Т6 | Данные только из §0 | ручная правка затирается следующим `sync` |
| Т7 | UTF-8 без BOM, LF, последний байт `0x0A` | уже проверяется в `sync.mjs` |
| Т8 | Экранирование всего пользовательского текста | `esc()` обязателен для любого значения из файлов |
| Т9 | Тема dark (текущая) | `data-theme="dark"` |
| Т10 | Один раздел = один `<section id="...">` | id из §2 |

**Т8 — критично.** В центре будут сообщения коммитов и цели спеков — текст, который
пишут люди и агенты. `esc()` в `sync.mjs` уже экранирует `& < > " '`; новый код
обязан использовать его для **каждого** подставляемого значения. Спека `010`
(jsdom smoke-тесты центра) должна проверять именно это.

**Т3 — уточнение.** «Без фреймворков» относится к странице центра. Приложение
LinuxExam (React + Vite) — отдельный продукт; центр на него не ссылается.

## 4. Доступность и читаемость

Наследуется от текущего центра (не регрессировать):

- контраст текста ≥ 4.5:1 (текущая палитра: `#FFFFFF` на `#1E1E1E`);
- `color-scheme: dark` + `lang="ru"`;
- моноширинный шрифт для SHA, id, ratio, exit-кодов;
- `tabular-nums` для чисел — уже есть в `.mono`;
- разделы — `<section>` с `<h2>`: экранный диктор может навигироваться по разделам;
- длинные сообщения коммитов: обрезка по словам, полный текст в `title` (тултип).

## 5. Производительность

Центр генерируется на каждый `npm run sync`, то есть после каждой задачи.

| Операция | Стоимость | Решение |
|---|---|---|
| `git log -20` | миллисекунды | вызывать напрямую |
| `git rev-parse HEAD` | миллисекунды | уже вызывается |
| чтение `specs/*.md` | ~11 файлов | уже читается |
| чтение `audits/*` | ~4+ файлов | только `readdir` + шапка, не полный парс |
| **`sync.mjs --check` изнутри `sync`** | полный прогон логики | **не запускать рекурсивно** — вычислить `inSync` по факту записи (как сейчас) |

**Ключевое ограничение:** раздел §2.1 обещает «статус sync (зелёный/красный)», но
`sync.mjs` не может честно проверить сам себя изнутри. Два варианта:

1. показывать статус по факту последнего успешного `--check` (из
   `state.json.gates.sync_check`), честно помечая время проверки;
2. показывать `inSync` текущего прогона (как сейчас) — это **не** проверка, а
   самоотчёт.

**Рекомендация:** вариант 1 + `state.json.gates.sync_check` (§9). Тогда шапка
показывает «проверено в 12:31» и не врёт.

## 6. Что НЕ делает центр

- **Не управляет.** Никаких кнопок, approve, запуска ролей. Решения капитана —
  через чат/Web, центр только **показывает**.
- **Не пишет в источники.** Центр — лист-артефакт; вход только на чтение.
- **Не содержит секретов.** Ни токенов, ни путей вне репозитория.
- **Не дублирует приложение.** Центр — про процесс, приложение — про пользователя.
- **Не показывает содержимое банка.** Вопросы — в `src/data`, не в центре.

- [ ] `npm run sync:check` exit 0; `typecheck`, `test:run` без регрессий;
- [ ] `docs/index.html` остаётся одним файлом (Т1).

  - name: orchestrator
    title: Orchestrator
    status: active                 # active | planned | deferred
    preset: linuxexam-orchestrator # пресет живёт ВНЕ репозитория

      human: "старт сессии; заявка капитана на задачу"
      check: "session_start"       # машинночитаемое условие либо null
    model_note: "модель задаётся per-session, не пресетом (DECISIONS M2.2c-1)"

  - name: content-writer
