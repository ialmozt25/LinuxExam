# spec 040 / t9 — repair B (round 2): F7 — m02 не должен давать hard-fail

**Задача:** t9 — ремонт находки F7 qc-раунда 1 (`.project/drafts/spec-040-qc-report.md`, §5)
**Файл:** `.project/scripts/validate-spec.mjs` (собственный артефакт t1 того же исполнителя)
**Дата:** 2026-10-01
**Итог:** F7 устранён; 15 проверок сохранены; hard-fail остался ровно в двух случаях —
нечитаемый frontmatter (m01) и сироты traceability (Фаза 4).

---

## 1. Формулировка F7 (что было не так)

До ремонта exit-политика была привязана к **литеральным id** проверок:

```js
const structuralFail = checks.some((c) => c.status === 'FAIL' && (c.id === 'm01' || c.id === 'm02'));
```

Из-за этого любое расхождение frontmatter `id`/`slug` с именем файла спеки
блокировало конвейер (`exit 1`): в qc-раунде 1 фикстур с `id: 900` в файле
`900-qc-adhoc.md` и `slug: qc-adhoc-t6` получил FAIL m02 и hard-fail, и qc был
вынужден переименовывать фикстур, чтобы прогнать apply-ветку. Расхождение
id/slug — дефект **оформления**, а не признак нечитаемой спеки: поля
`id/type/status` читаются, спека дальше адресуема, имя файла поправимо
переименованием.

## 2. Что изменено в `.project/scripts/validate-spec.mjs`

1. **Введён машиночитаемый уровень влияния** у каждой проверки Фазы 1
   (б. 487–496): `add(id, name, status, issues, note, severity)`, где
   `severity: 'hard-fail' | 'diagnostic'` (по умолчанию `'diagnostic'`).
   Политика exit-кода больше не ищет литеральные id: она смотрит на объявленный
   уровень.

2. **m01 — единственный hard-fail уровня Фазы 1** (б. 498–522): `severity`
   становится `'hard-fail'`, только если frontmatter реально нечитаем —
   нет открывающего блока `---`, блок не закрыт, либо отсутствует поле `id`
   (спека неадресуема). Любые другие срабатывания m01 остаются диагностикой.
   В отчёте такая проверка печатается как `[FAIL (hard-fail)]`.

3. **m02 явно объявлен диагностикой** (б. 524–546): комментарий фиксирует
   решение F7, вызов стал
   `add('m02', …, 'diagnostic')`. Статус проверки остался `FAIL`
   (диагностика сохраняется), но exit-код она не меняет. **Имя проверки и id
   не изменились.**

4. **Exit-политика переведена на severity** (б. 1512–1526):

   ```js
   const structuralFail = checks.some((c) => c.status === 'FAIL' && c.severity === 'hard-fail');
   ```

   Hard-fail = сироты traceability (Фаза 4) ИЛИ FAIL-проверка с
   `severity: 'hard-fail'` (сейчас это только m01). Комментарий перечисляет
   ровно два случая.

5. **JSON-отчёт** (б. 1560–1568) печатает `severity` рядом с `status` каждой
   проверки, чтобы машиночитаемый контракт совпадал с политикой.

6. **Ремонт регрессии критерия 9** (б. 1128–1136): из корпуса свидетелей
   канала «уже выполнено в репозитории» исключён `/.project/drafts/**` —
   генерируемые артефакты прогонов (промпты, отчёты фаз, отчёты qc). Причина
   ниже, §4; без этой правки критерий 9 spec 040 становился сиротой и давал
   ложный hard-fail.

Изменения в отчётной части: FAIL-проверки с уровнем `hard-fail` печатаются как
`[FAIL (hard-fail)] m01 …` (б. 1360–1365) — иначе диагностический FAIL m02 и
блокирующий FAIL m01 выглядели одинаково.

## 4. Ремонт регрессии критерия 9 (почему тронут корпус свидетелей)

При первом прогоне после правки exit-политики spec 040 стал давать
`exit 1` из-за **сироты критерия 9** — это не следствие F7, а накопленный
дефект канала «уже выполнено в репозитории»:

```
ДО ремонта корпуса (политика t6 + корпус без исключения):
BASELINE SCORE: 85/100
Сироты: цели 0, критерии 1, задачи 0
Результат: HARD-FAIL (exit 1)          ← before-040-t6state.txt
```

Причина: канал ищет свидетеля по «редким» токенам критерия, а порог редкости
считается от размера корпуса (`max(3, files × 0.15)`). Мои же артефакты
прогонов в `.project/drafts/spec-040/t6-run*` (промпты, `report.md`) добавили
десятки файлов, содержащих слова `score`, `sources`, `findings`: корпус вырос
191 → 252 файла, порог 28.6 → 37.8, токен `score` стал «частым» (63 файла при
пороге 37.8), из четырёх редких токенов остался один — и функция
`repoEvidence` вернула `null`. Итог: критерий «Отчёт содержит score до/после,
diff, tiered sources, findings» перестал находить свидетеля
`docs/spec-chain/skills/spec-enrich/SKILL.md` и стал сиротой.

Измерения (диагностика `t9diag3`):

| корпус | файлов | порог | редкие токены критерия 9 | свидетель |
|---|---|---|---|---|
| без исключения | 252 | 37.8 | `tiered` (score=63, sources=38, findings=54 — частые) | нет → сирота |
| `.project/drafts/**` исключён | 119 | 17.8 | `score, tiered, sources, findings` | `docs/spec-chain/skills/spec-enrich/SKILL.md` |

Правка: `if (/^\.project\/drafts\//.test(rel)) continue;` (б. 1134) с
комментарием-обоснованием. Генерируемые отчёты прогонов — не свидетельства о
спецификации; их исключение делает канал устойчивым к накоплению артефактов и
не расширяет покрытие (корпус только сжимается). После правки:

```
кр.9 (стр. 174) -> уже выполнено в репозитории (docs/spec-chain/skills/spec-enrich/SKILL.md)
Сироты: цели 0, критерии 0, задачи 0
Результат: PASS (exit 0)
```

Важно: негативный контроль A3 (`913-orphan-criterion.md`) подтверждает, что
канал не стал «всеядным» — сирота критерия по-прежнему даёт hard-fail.

## 6. Остаточные риски и границы

- **`m04` (DAG) остаётся диагностикой.** После F7 hard-fail уровня Фазы 1 даёт
  только m01. Это соответствует контракту t9 («hard-fail ровно для двух
  случаев»), но фикстуры qc-раунда 1, ожидавшие `exit 1` на неизвестной
  зависимости `t8` (F6 в `spec-040-qc-report.md`), теперь получают `exit 0`.
  Если для цепочки нужен жёсткий DAG-гейт — это отдельное решение (можно
  выставить m04 `severity: 'hard-fail'` одной строкой), вне контракта t9.
- **Порог редкости токенов зависит от размера корпуса.** После исключения
  `.project/drafts/**` корпус стабилен (119 файлов), но новые каталоги с
  отчётами в `.project/**` или `docs/**` снова сдвинут порог. Кандидат на
  будущий ремонт — фиксировать порог или считать его от «нормативных»
  документов.
- **F2/F3/F4/F5/F6/F8** из отчёта qc-раунда 1 не входят в t9 и не тронуты.
- Правки касаются только `.project/scripts/validate-spec.mjs`; вне inScope
  (`enrich-spec.mjs`, `docs/spec-chain/**`, `.project/specs/**`,
  `.project/sync.mjs`, `src/**`, `tools/**`, `package.json`) ничего не менялось.
