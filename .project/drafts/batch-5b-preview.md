## 2. Полный текст кандидатов

### `sh_011` — case: выбор ветки по шаблону (medium)

**Вопрос:** Скрипт /usr/local/bin/start.sh получает первым аргументом одно из слов: start, stop или status. Какая конструкция выберет ветку по значению этого аргумента?

| | опция | верно |
|---|---|---|
| 1 | `case $1 in start) systemctl start app;; esac` | ✅ |
| 2 | `case $1 of start) systemctl start app;; esac` | — |
| 3 | `case $1 if start) systemctl start app;; esac` | — |
| 4 | `case $1 when start) systemctl start app;; esac` | — |

**Explanation:** Многоветвевой выбор в shell открывается словом case, продолжается словом in, а закрывается esac; шаблон и закрывающая скобка отделяют ветку, а две точки с запятой завершают её. Слов of в синтаксисе case нет — оболочка сообщит об ошибке разбора. Слово if относится к условному оператору и внутри case не работает. Слово when не является ключевым в shell: оно встречается в других языках, но не в разборе case.

### `sh_012` — getopts: разбор опций запуска (medium)

**Вопрос:** Скрипт /usr/local/bin/pack.sh должен принимать флаг -v без значения и опцию -o со значением. Какая строка начнёт разбор этих опций?

| | опция | верно |
|---|---|---|
| 1 | `while getopts "vo:" opt; do echo $opt; done` | ✅ |
| 2 | `while getopts "v:o" opt; do echo $opt; done` | — |
| 3 | `while getopts "vo:" $opt; do echo $opt; done` | — |
| 4 | `getopts "vo:" opt; do echo $opt; done` | — |

**Explanation:** В строке шаблона getopts двоеточие после буквы означает, что эта опция требует значения. Запись vo: описывает ровно требуемое: -v без значения и -o со значением, которое попадёт в переменную OPTARG. Запись v:o переставляет двоеточие и делает наоборот — значение требует -v, а -o его не принимает. Запись с $opt во втором аргументе подставляет значение переменной там, где getopts ждёт её имя. Вызов без while разберёт только первую опцию и на этом закончится.

### `sh_013` — trap: обработчик завершения (medium)

**Вопрос:** Скрипт /usr/local/bin/run.sh создаёт временный файл /tmp/run.lock и должен удалять его при завершении, в том числе при прерывании. Какая строка зарегистрирует такой обработчик?

| | опция | верно |
|---|---|---|
| 1 | `trap "rm -f /tmp/run.lock" EXIT` | ✅ |
| 2 | `trap EXIT "rm -f /tmp/run.lock"` | — |
| 3 | `trap "rm -f /tmp/run.lock" STOP` | — |
| 4 | `catch "rm -f /tmp/run.lock" EXIT` | — |

**Explanation:** У trap первым аргументом идёт команда-обработчик, вторым — событие: запись с EXIT выполнит удаление при любом штатном и аварийном завершении скрипта. Перестановка аргументов заставит оболочку искать команду с именем EXIT. Событие STOP не перехватывается оболочкой, поэтому обработчик не сработает. Команды catch в shell нет: перехват событий выполняет только trap.

### `sh_014` — set -e: остановка при ошибке (medium)

**Вопрос:** Скрипт /usr/local/bin/deploy.sh должен прекращать работу, как только любая его команда завершилась с ненулевым кодом. Какая строка в начале скрипта это обеспечит?

| | опция | верно |
|---|---|---|
| 1 | `set -e` | ✅ |
| 2 | `set -x` | — |
| 3 | `set -u` | — |
| 4 | `set -v` | — |

**Explanation:** Ключ -e включает режим немедленного выхода: команда с ненулевым кодом завершает скрипт. Ключ -x включает трассировку и на реакцию на ошибку не влияет. Ключ -u завершает скрипт только при обращении к неустановленной переменной. Ключ -v печатает строки по мере чтения, то есть управляет лишь выводом.

### `sh_015` — source: выполнение в текущей оболочке (easy)

**Вопрос:** Администратор набрал в интерактивной оболочке чтение файла /etc/profile.d/settings.sh, где заданы переменные окружения, и хочет, чтобы они остались в этой же сессии. Какую строку он введёт?

| | опция | верно |
|---|---|---|
| 1 | `source /etc/profile.d/settings.sh` | ✅ |
| 2 | `bash /etc/profile.d/settings.sh` | — |
| 3 | `sh /etc/profile.d/settings.sh` | — |
| 4 | `exec /etc/profile.d/settings.sh` | — |

**Explanation:** Команда source читает файл и выполняет его строки в текущей оболочке, поэтому присваивания остаются в ней и после возврата. Запуск через bash выполняет файл в подоболочке: переменные исчезают вместе с ней. Запуск через sh даёт тот же результат, но другой интерпретатор. Команда exec заменяет текущую оболочку указанным файлом, поэтому вернуться в скрипт уже не получится.

### `sh_016` — bash -n: проверка синтаксиса (easy)

**Вопрос:** Файл /usr/local/bin/gather.sh содержит триста строк и недавно правился вручную. Прежде чем запускать его на сервере, администратор хочет убедиться, что синтаксис не сломан, и при этом ничего не выполнять. Что он введёт?

| | опция | верно |
|---|---|---|
| 1 | `bash -n /usr/local/bin/gather.sh` | ✅ |
| 2 | `bash -x /usr/local/bin/gather.sh` | — |
| 3 | `bash -v /usr/local/bin/gather.sh` | — |
| 4 | `bash -e /usr/local/bin/gather.sh` | — |

**Explanation:** Ключ -n переводит bash в режим чтения без выполнения: оболочка разбирает файл целиком и сообщает о синтаксических ошибках, но ни одной команды не запускает. Ключ -x выполняет скрипт и печатает трассировку каждой команды. Ключ -v печатает строки по мере чтения, но выполнение продолжается. Ключ -e лишь меняет реакцию на ошибку во время работы.

## 2a. Правка после approve (QC rework двух вопросов)

**Что произошло.** После интеграции `qc` на банке 218 дал **Fails 2** (базлайн — 0):
`sh_012`, пары опций 0/2 и 1/3 с bigram jaccard **1.00**. Причина не в содержании, а во
взаимодействии с гейтом: токенизатор `tools/qc.cjs` срезает с краёв токена класс
символов `,.;:!?()[]{}"'`, поэтому у опции `while getopts "vo:" opt …` двоеточие попадает
внутрь хвостовой пунктуационной серии и удаляется вместе с кавычкой — `"vo:"` и `"vo"`
дают один токен `vo`, а `"v:o"` и `"v:o:"` — токен `v:o`. Четыре опции схлопывались в две
токен-идентичные пары. Дополнительно 4 WARN у `sh_011` из-за пробела перед `;;`
(правило `/\s+[,;:!?]/`).

**Что изменено** (только внутри `sh_011`..`sh_016`, прямо разрешённых заданием):

| id | было | стало | почему |
|---|---|---|---|
| `sh_011` | `case $1 in start) systemctl start app ;; esac` (и 3 таких же) | `case $1 in start) systemctl start app;; esac` | пробел перед `;;` давал 4 WARN; синтаксис bash остаётся корректным, токены и jaccard не меняются |
| `sh_012` | опции `"vo"` и `"v:o:"` как дистракторы | `while getopts "vo:" $opt; do echo $opt; done` (значение вместо имени переменной) и `getopts "vo:" opt; do echo $opt; done` (без цикла) | исходные дистракторы были токен-идентичны верной опции после срезания пунктуации |

Стем, subtopic, сложность и проверяемый механизм `sh_012` (правило двоеточия в `getopts`)
сохранены; изменены только две дистракторные опции и explanation. Итог после правки:
`ratio` 1.045 (`sh_011`) и 1.189 (`sh_012`), все пары jaccard ≤ 0.75, **QC PASS:
Total 218, Fails 0, Warns 22** — ровно базлайновое число предупреждений.

**Порядок был воспроизводимым:** `src/data` откачен к HEAD, кандидаты перепроверены
оффлайн-копией правил `qc.cjs`, затем интеграция выполнена заново тем же скриптом.

Это изменение контента **после** approve. Формально оно в рамках задания («контент
**кроме** `sh_011..sh_016`» + критерий «`Fails 0`»), но зафиксировано явно — здесь,
в `log.md` и в spec 018, — чтобы капитан мог откатить (`git revert`, правило 8).

## 4. Avoid-list, применённый при написании

Собран из `.project/log.md`, `.project/factory/MEMORY-FACTORY.md` (раздел «Уроки») и
`.project/audits/bank-audit-2026-09-27.md`. Что реально повлияло:

- **Ограничение схемы вариантов.** `tools/qc.cjs` считает placeholder'ом любую опцию или
  стем с `[...]`, `{...}` или `<...>`. Поэтому в опциях батча нет ни `[[ ]]`, ни
  `${VAR:-значение}`, ни brace-expansion — пришлось отказаться от двух запланированных
  subtopic'ов («строгое сравнение `[[ ]]`» и «значение по умолчанию через `${VAR:-…}`»),
  хотя они методически хороши. По той же причине в банке используется `test $# -eq 2`,
  а не `[ $# -eq 2 ]`: проверка placeholder'а валит второй вариант.
- **Паритет длин опций.** Все четыре опции каждого вопроса построены по одному шаблону,
  отличие — ровно один смысловой токен (`in`/`of`/`if`/`when`, место двоеточия, имя
  сигнала, буква ключа). Это держит ratio в 1.000–1.138 при порогах 1.30 (`sentences`) и
  2.00 (`token`) — не «подгонка под порог», а отсутствие подсказки по длине.
- **`sh_004`~`sh_007` (0.8311)** — учтено в avoid-list: новые вопросы сознательно не
  используют ни `list.txt`, ни слово «строки» в стеме, чтобы не усилить этот кластер.
- **`tf_001`~`tf_002` (0.9020)**, `ms_002`~`ms_008` (0.8527), `ug_002`~`ug_018`,
  `ds_013`~`pm_014` — аномалии чужих тем; на всякий случай батч прогнан против **всего**
  банка (212), а не только против своей темы.
- **Урок «среда верификации важнее дисциплины»** — поведение ключей описано по
  документации GNU/bash, без исполнения на Rocky 9 (среда DSH — Windows/PowerShell);
  см. §6.

## 6. Риски и места, где нужен человеческий взгляд

1. **Проверка только по документации.** Команды выверены по знанию bash 5.1 / GNU
   coreutils, **без исполнения на Rocky 9** (среда DSH — Windows/PowerShell). Все
   конструкции стандартные и переносимые, но это утверждение, а не замер.
2. **Переносимость `source`.** В POSIX-оболочке (`dash`, `/bin/sh`) команды `source` нет —
   там работает точка (`.`). В банке спрашивается про `source`, что корректно для
   bash/Rocky 9 и для интерактивной сессии администратора; дистрактор `.` сознательно не
   использован, в том числе потому что опция, начинающаяся с точки, ломает semi-критерий 7
   Haladyna (все опции должны начинаться с команды-слова).
3. **Haladyna MANUAL 9, 10** (соответствие цели экзамена, отсутствие «trick question»)
   автоматикой не проверяются — это субъективные критерии, их закрывает проверяющий.
   Ниже — результат независимой проверки содержания (второй агент, отдельный от писателя).
4. **`getopts`** — тонкий, но классический вопрос про двоеточие; сложность признана
   «medium» осознанно. Если капитан считает его «слишком тёмным» для целевой аудитории,
   замена на более простой механизм (`shift`) возможна без перестройки батча.

  полноте разбора.
- **`sh_012`** — `echo $opt` без кавычек; в контексте вопроса косметика.
- **`sh_014`** — `set -e` не является жёсткой гарантией: он отключается в условиях
  `if`/`while`, в цепочках `&&`/`||` (кроме последнего звена), при отрицании и в
  подстановках. Для вопроса это не дефект (стем описывает **цель**, а верная опция —
  единственная, включающая этот режим); формулировка explanation смягчена («первая же
  команда… и выполнение дальше не идёт» → «команда с ненулевым кодом завершает скрипт»).

Про переносимость (из того же ревью): ни один вопрос **не требует** bash-only-расширения
для правильного ответа. `case…in`, `getopts "vo:"`, `set -e/-x/-u/-v` — полностью POSIX;
`trap … EXIT` вне POSIX (POSIX задаёт только `0`), но dash/ksh/mksh/bash принимают его
одинаково. Единственная по-настоящему bash-специфичная конструкция — `source` в `sh_015`;
это приемлемо, потому что стем говорит об интерактивной оболочке на целевой Rocky Linux 9.
