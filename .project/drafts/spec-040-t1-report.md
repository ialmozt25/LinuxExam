## 1. Что сделано

Создан детерминированный CLI-валидатор спек — ядро Компонента A spec 040
(из 11 фаз реализованы Фазы 0, 1, 4; фазы 2–10 — LLM-часть скилла
`spec-enrich`, вне скоупа t1).

Технические характеристики:

- Node ESM (`.mjs`), запускается как `node .project/scripts/validate-spec.mjs <spec>`;
- **zero-deps**: только встроенные модули `node:fs`, `node:path`, `node:url`;
- **без сети**: ни `fetch`, ни `http`, ни `child_process` — сетевых вызовов нет;
- **read-only**: валидатор не пишет в репозиторий (единственная запись — файл,
  явно указанный флагом `--out`);
- 1585 строк, включая развёрнутые комментарии к каждому правилу;
- весь вывод на русском, маркеры `PASS`/`FAIL`/`WARN`, без emoji;
- детерминированная политика exit-кодов: `0` — чисто, `1` — hard-fail,
  `2` — ошибка использования/чтения.

Резолв аргумента: принимается и путь к спеке
(`.project/specs/040-spec-chain.md`), и её id (`040`). Резолв относительно корня
репозитория (определяется от `.project/scripts/`, не от `cwd`), поэтому команда
работает из любого каталога.

### 1.1. Фаза 0 — baseline score (0–100)

Пять измерений с весами **Completeness 30 / Clarity 25 / Testability 25 /
Consistency 10 / Scope 10** (сумма ровно 100). Каждое измерение набирает
сырые баллы, нормируется в 0–100% и вносит вклад `норма × вес / 100`:

| измерение | вес | что проверяет |
|---|---|---|
| Completeness | 30 | секции Контекст / Цель / Что делаем / Критерии приёмки / Декомпозиция / Источники / Edge Cases / Что НЕ трогать + глубина «Контекста» (>= 5 содержательных строк) |
| Clarity | 25 | длина предложений (> 45 слов), vague terms («и т.д.», «нормально», «по возможности»…), открытые вопросы и `[citation needed]` (снижение только если спека не декларирует фазу, которая их закрывает), структура «Что делаем» по компонентам |
| Testability | 25 | наличие критериев приёмки, доля критериев с проверяемым признаком, доля критериев с verify-командой (`node`/`npm`/`grep`/`git`/`exit N`), явная секция Verify |
| Consistency | 10 | поля frontmatter, нумерация фаз 0…N без пропусков, разрешимость cross-refs на `.md`, `status` из допустимого набора |
| Scope | 10 | write-скоупы задач, объявленные зависимости задач, зафиксированная граница записи |

Итог: `BASELINE SCORE: N/100` и вердикт относительно порога 70.

### 1.2. Фаза 1 — ровно 15 механических проверок

Ровно 15 проверок с фиксированными id `m01`…`m15`; при FAIL печатается
`путь:строка` и причина.

| id | проверка | что ловит |
|---|---|---|
| m01 | frontmatter: блок `---` и поля id/slug/type/status/commit | отсутствие/незакрытый frontmatter, пропущенное поле |
| m02 | id/slug спеки согласованы с именем файла | `id: 040` при файле `041-…md` |
| m03 | секция «## Декомпозиция» присутствует | отсутствие DAG → **WARN**, не падение |
| m04 | DAG декомпозиции: известные зависимости, без дублей и циклов | ссылка на несуществующую задачу, self-dep, дубль id, цикл, задача раньше своей зависимости |
| m05 | уникальность id спеки в `.project/specs` | две спеки с одним `id` |
| m06 | существование путей, упомянутых в спеке | битая ссылка на путь (deliverables спеки и usage-примеры исключены) |
| m07 | placeholder-маркеры (`TBD`/`TODO`/`FIXME`/`<id>`/`[citation needed]`) | незакрытые заглушки → **WARN** |
| m08 | self-reference: спека не пишет сама в себя | задача правит `.project/specs/<своя спека>` |
| m09 | write-scope overlap: задачи не делят файлы, не пишут в «НЕ трогать» | два writer'а на один файл, запись в запретную зону |
| m10 | поле commit/SHA согласовано со статусом спеки | `commit` не SHA, `status: done` с `commit: null`, неизвестный статус |
| m11 | критерии приёмки: наличие и проверяемость каждого | нет секции/пусто, дубль номера, критерий без проверяемого признака |
| m12 | обязательные секции: Контекст/Цель/Что делаем/Критерии приёмки | отсутствие несущей секции |
| m13 | критерии приёмки содержат verify-команды | ни одного исполняемого критерия |
| m14 | edge cases описаны (секция + непустой список) | нет секции или пустой список |
| m15 | внутренние ссылки (спеки, документы) разрешаются | `spec 999`, ссылка на несуществующий `.md` |

Примечание к счётчику: `grep -c "add('m"` даст 15 совпадений. Кириллические
заголовки в проверках сопоставляются через `(?![\p{L}\p{N}_])`, потому что
`\b` в JS ASCII-центричен и с русским текстом не матчится (это была первая
найденная и исправленная ошибка реализации).

### 1.3. Фаза 4 — traceability Цель → Критерий приёмки → Задача декомпозиции

Три уровня с явной классификацией каждой связи (в отчёте видно, *почему*
критерий считается покрытым):

1. **Критерий → задача**, по приоритету каналов:
   - `id:` — в тексте критерия явно назван id задачи (`t3`);
   - `atom:` — критерий называет артефакт, который задача доставляет
     (полный путь или имя файла, включая write-скоупы задачи);
   - `phase:` — критерий про «Фазу N» и задача владеет диапазоном фаз
     («Фазы 2, 3, 5–10»);
   - `role:` — критерий про `verdict`/qc/reviewer, и задача за этой ролью;
   - `token:` — строгий токен-фолбэк: редкий технический термин (df <= 3,
     длина >= 7) либо >= 2 общих токена длиной >= 5; одиночные
     общеупотребительные слова («спека», «задача») связи не создают.
2. **Уже выполнено в репозитории** — критерий называет файл-артефакт, и этот
   файл существует с подтверждающим содержанием (например
   `.project/DECISIONS.md` для п.8) либо все редкие токены критерия собраны в
   одном файле-отчёте/скилле. Свидетель указывается в отчёте.
3. **Вне DAG** — критерий про операцию капитана, внешний репозиторий
   (`~/.dsh/…`) или финальный гейт (`sync:check`, `test:run`, `verdict=`).

Hard-fail: **сирота уровня «цель»** (нет ни одной связи с критерием/задачей) или
**сирота уровня «критерий»** (нет ни задачи, ни внешнего владельца, ни
доказательства из репозитория) → `exit 1` и явное сообщение `HARD-FAIL …`.
Задача без критерия → WARN (инфраструктурные работы законны).

### 1.4. Флаги

- без флагов — человекочитаемый отчёт только в stdout;
- `--json` — машиночитаемый отчёт в stdout (человекочитаемая форма подавляется);
- `--out <path>` — запись отчёта в файл (форма зависит от `--json`), в stdout
  остаётся только строка `отчёт записан: <path>`;
- `--help` — usage, exit 0.

### 1.5. Политика exit-кодов (осознанное решение)

`exit 1` дают только **сироты traceability** и **структурно нечитаемый
frontmatter** (m01/m02). Механические FAIL уровня «качество текста»
(заглушки, недоступные пути, критерии без verify-команды) остаются
диагностикой в отчёте и exit-код не меняют: спека может быть одобрена
капитаном и нести заведомо известные долги, которые закрывает Фаза 2
(например `[citation needed]` в spec 040 прямо помечены как «URL добавить при
первом прогоне spec-enrich»). Иначе baseline всегда падал бы и цепочка
run-spec-chain не стартовала бы вовсе.

## 4. Known limitations

1. **Объём > ~500 строк** (1585). Референсный размер был ориентиром; правила
   Фазы 0/1/4 с подробными комментариями, единым каналом свидетелей и
   диагностикой по каждой проверке в 500 строк не укладываются без потери
   читаемости. Дифф не затрагивает ничего за пределами in-scope.
2. **Baseline score spec 040 = 85/100, а не «низкий» черновой балл.** Первая
   версия рубрики давала 29/100 из-за ложных срабатываний на кириллице
   (`\b` не матчит русские заголовки) и жёстких штрафов за `[citation needed]`
   и список «Что НЕ трогать». После исправления рубрика стала строгой, но
   справедливой. Практическое следствие: метрика DECISIONS «score delta >= +20»
   на спеке 040 недостижима в этом измерении — дельта будет считаться от 85.
   Это нужно учесть в t4/t6 при демонстрации «score delta > 0».
3. **`[citation needed]` в spec 040 (строки 29, 31) — WARN, не FAIL.** Рубрика
   снижает Clarity только на 4 из 6 баллов, если спека прямо декларирует, что
   заглушки закрывает Фаза 2. Настоящая проверка «Фаза 2 выполнилась» —
   критерий приёмки 10 spec 040 и относится к t2/t6, а не к детерминированному
   ядру.
4. **Канал «уже выполнено в репозитории» — эвристика, а не доказательство
   корректности.** Он не ослабляет главную проверку (критерий → задача), но
   может признать критерий покрытым по существующему файлу-свидетелю
   (кр.8 → `.project/DECISIONS.md`, кр.9 → `.../spec-enrich/SKILL.md`).
   Поэтому канал печатает свидетеля в отчёте и включается только когда задачи
   не нашлось. В JSON/Narrative поле `external` содержит такие критерии
   наравне с внешними владельцами.
5. **Токен-фолбэк (канал 5) — грубая эвристика.** Требование «редкий термин
   (df <= 3, длина >= 7) или >= 2 общих токена длиной >= 5» заметно снижает
   ложные связи, но не исключает их (например кр.2 → `t1(token:baseline)` —
   связь по одному слову «baseline»; содержательно критерий ближе к t1/t6).
   Направление ошибки безопасное: ложная связь скрывает сироту, обратная
   ошибка (объявить сироту у здоровой спеки) на spec 040 не воспроизводится.
6. **Парсер декомпозиции знает две исторические формы** —
   `1. id: t1, subject: …; assignee: builder, dependencies: []` (specs 038–040) и
   `` 1. `id: t1` · `subject: …` · `assignee: …` `` (specs 034–037). Иные формы
   дадут «задача без id» и, следовательно, ложных сирот.
7. **Чужие закрытые спеки дают hard-fail — это ожидаемо.** Валидатор без
   скидок применяет правила к любой спеке: `038` → сирота критерия 5
   (`npm run spec:close -- --help` — требование `--help` не закреплено ни за
   одной задачей), `036`/`039` → 2–3 сироты. Эти спеки закрыты, их
   декомпозиции уже не актуальны; гейт на них никто не наводит. Exit 0
   требуется только для spec 040 (и для «чистых» спек в целом).
8. **Фазы 2, 3, 5–10 не реализованы** — это LLM-часть (research/enrich,
   fact-check, семантика, adversarial, simulation, regeneration, repair loop,
   external audit) и живёт в `docs/spec-chain/skills/spec-enrich/SKILL.md`
   (t2) + обёртке `.project/scripts/enrich-spec.mjs` (t4).
