# Ops: роль DevOps — ответственность, границы, эскалация

Дата: 2026-09-28
Контекст: M6.0 Фаза 3, spec `008-devops-role-document` (`approved`). Роль описана
**документом**, а не DSH-пресетом (почему — раздел «Причина»).

## Проблема

В проекте устойчив паттерн «роль = DSH-пресет» (Content Writer, QC Auditor), и по
инерции ops-роль тоже тянуло оформлять пресетом. При этом у неё нет ежедневной
нагрузки, а её работа (релиз, бэкап, триаж зависимостей, гейты перед релизом)
размазана по чужим артефактам и нигде письменно не закреплена. Последствие без
документа: «кто отвечает за деплой без гейтов / за 52 уязвимости / за restore drill»
решается вкусом в каждой сессии, а решение «документ или пресет» не проверяемо.

## Причина

1. **Пресет не задаёт модель.** `readPresetMetadata()` читает только `name`,
   `description`, `order`; поле `model:` молча отбрасывается (DECISIONS
   `2026-09-26 — QC Auditor: reference-копия, модель, YAML, pwsh-ловушка`). То есть
   «изоляция модели» через пресет не достигается — а это одна из причин заводить роль
   пресетом.
2. **Пресет — дорогой артефакт.** Требует сброса/перезапуска DSH и живёт вне
   репозитория (только reference-копия в `docs/knowledge/dsh/presets/linuxexam-qc-auditor/`).
   Для роли без регулярной нагрузки это стоимость без отдачи.
3. **У базы знаний нет раздела `ops/`.** Практики по DSH задокументированы
   (`docs/knowledge/dsh/`), а эксплуатационные — нет; писать роль было некуда.

## Решение

Роль DevOps существует как **документ базы знаний**: `docs/knowledge/ops/devops-role.md`
(этот файл), каталог `docs/knowledge/ops/` — рядом с `docs/knowledge/dsh/`. Пресет для
роли **не создаётся**, пока не сработал триггер эскалации (раздел ниже).

### Чем роль владеет

1. **Релиз и деплой.** Единственный пайплайн — `.github/workflows/deploy.yml`
   (GitHub Pages): триггер `push` в `main` + `workflow_dispatch`; шаги
   `actions/checkout@v4` → `actions/setup-node@v4` (Node `'22'`, `cache: npm`) →
   `npm ci` → `npm run build` с `VITE_BASE=/LinuxExam/` и `CI: true` →
   `actions/upload-pages-artifact@v3` (path `dist`) → `actions/deploy-pages@v4`
   (job `deploy` только при `github.ref == 'refs/heads/main'`).
   Прод — `https://ialmozt25.github.io/LinuxExam/`. По правилу 4 `.project/ORCH-RULES.md`
   прод **не трогается без approve капитана**, `git push` — отдельный approve.
2. **Бэкап.** NAS-бэкап и restore drill — milestone **M4** (`.project/PLAN.md`:
   «M4: NAS-бэкап + Patterns Library»; в `.project/state.json` → `milestones` M4 =
   `planned`). Роль владеет процедурой бэкапа и **регулярной проверкой
   восстановления** (drill), а не только созданием копии.
3. **Гигиена зависимостей.** Пункт `.project/BACKLOG.md`: «Dependabot: 52 уязвимости
   в default branch (1 critical, 23 high, 24 moderate, 4 low) — проверить и обновить
   зависимости». Роль владеет триажем и одним из трёх решений на находку:
   **обновить**, **принять риск (с записью)**, **зафиксировать в `BACKLOG.md`**.
4. **Гейты перед релизом.** `npm run state:update` (`.project/../tools/gen-state.mjs`)
   прогоняет и записывает в `state.json.gates` четыре гейта:
   `qc` (`node tools/qc.cjs`), `typecheck` (`tsc --noEmit -p tsconfig.app.json`),
   `vitest` (`vitest run` = `npm run test:run`), `shuffle_bank`
   (`node tools/shuffle-bank.mjs --check`). Роль отвечает за то, чтобы релиз не уезжал
   на красном; DOD (`.project/DOD.md`) — что требуется перед коммитом.
5. **Секреты и конфигурация окружений.** Что нельзя коммитить:
   `node_modules`, `dist`, `.env` (AGENTS.md, «Запрещено»; `.gitignore` содержит
   `node_modules`, `dist`, `dist-ssr`, `.env`, `*.local`). На 2026-09-28 в репозитории
   нет ни одного `.env*`-файла, и это ожидаемое состояние: секретов в проекте нет,
   конфиг деплоя — переменные окружения job'а в `deploy.yml` (`VITE_BASE`, `CI`).
   Роль отвечает за то, чтобы секрет не появился в истории коммитов и в логах CI.
6. **Шум деплоя.** Пункт `BACKLOG.md`: `deploy.yml` без `paths-ignore` — doc-only push
   триггерит деплой Pages (предлагаемое исправление:
   `paths-ignore: ['docs/**', '*.md', '.project/**']`). Исправление принадлежит этой
   роли; сама правка `deploy.yml` в скоуп spec 008 **не входила** — это отдельная задача.

### Не-цели

Роль DevOps **не делает** следующего:

- **не пишет и не правит контент банка** (`src/data/questions/*`) — контент-трек
  закрыт (правило 6 `.project/ORCH-RULES.md`, freeze на 206 вопросах);
- **не принимает решений о контенте** — ни о составе банка, ни о правках вопросов,
  ни о порогах качества контента;
- **не правит `src/**` без спеки** — код приложения меняется только по spec
  (правило 1: без spec — нет задачи);
- **не делает push в прод без approve капитана** (правило 4) — включая деплой
  «на всякий случай» и ручной прогон `workflow_dispatch`;
- **не создаёт пресеты и не добавляет роли в пресеты** — это действие капитана.

### Триггеры эскалации до пресета

Документ остаётся документом, пока ни один триггер не сработал. Пресет создаётся
**только при явном срабатывании одного из них, и только по approve капитана**:

1. **Частота.** Роль вызывает DSH-агента ≥ 3 раза в неделю на протяжении ≥ 2 недель
   (считать по `.project/log.md` и `.project/drafts/`).
2. **Стандартный вход.** Появился повторяющийся вход (набор файлов + фиксированный
   набор команд), который каждый раз копипастится вручную.
3. **Ошибка из-за импровизации.** Зафиксирован инцидент, где агент без пресета сделал
   ops-действие иначе, чем описано в документе (пример: деплой без гейтов).
4. **Изоляция модели.** Возникла потребность в модели/фрейме, отличном от
   Orchestrator'а, и per-session `/model` перестал быть достаточным.

**Ограничение, которое нельзя забыть при эскалации:** пресет **не задаёт модель** —
`readPresetMetadata()` читает только `name`/`description`/`order`
(DECISIONS `2026-09-26 — QC Auditor: reference-копия, модель, YAML, pwsh-ловушка`).
Поэтому триггер 4 сам по себе пресетом **не закрывается**: нужен другой механизм
(например host-config или `model` в конфиге профиля), а не пресет.

## Как избежать

1. **Перед релизом — гейты, а не надежда.** Прогон `qc` / `typecheck` / `test:run` /
   `shuffle-bank:check` и `sync:check` = exit 0 (правило 3 `.project/ORCH-RULES.md`),
   только потом push в `main` — именно `push` в `main` запускает деплой Pages.
2. **Любая ops-правка — по спеке**, а не «по месту»: правило 1. Правки `deploy.yml`,
   `.github/**`, зависимостей и бэкап-процедуры оформляются спекой.
3. **Находка без владельца → строка в `BACKLOG.md`.** Не «забыли», а записано
   (иначе 52 уязвимости и `paths-ignore` живут годами).
4. **Секрет — только в окружении job'а.** Никаких `.env` в репозитории: `.env` есть в
   `.gitignore`, но правило сильнее игнора — файл не создаётся вовсе.
5. **Не превращать роль в пресет раньше триггера.** Пресет без нагрузки — это
   стоимость сброса DSH и ещё один артефакт вне репозитория.

## Проверка

- Документ на месте и находится из индекса: `docs/knowledge/README.md` содержит строку
  про `ops/`; файл — `docs/knowledge/ops/devops-role.md`.
- Ни одного нового пресета: `git status --porcelain -- docs/knowledge/dsh` пусто;
  каталог `docs/knowledge/dsh/presets/` содержит только `linuxexam-qc-auditor/`.
- Пайплайн и его шаги сверяются с файлом, а не с памятью:
  `Get-Content .github/workflows/deploy.yml`.
- Четыре гейта видны в состоянии: `npm run state:update` → `.project/state.json` →
  `gates` (`qc`, `typecheck`, `vitest`, `shuffle_bank`) с `exits`.
- Прод не тронут без approve: в `.project/log.md` нет записи push'а в прод без
  соответствующего решения капитана (правило 4).
