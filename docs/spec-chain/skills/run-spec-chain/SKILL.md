# run-spec-chain — оркестратор цепочки spec-фабрики

> Reference-скилл пресета `linuxexam-spec-chain` (spec 040, Компонент B;
> автономность STOP-точек A/B/D — spec 051).
> Активация: `/run-spec-chain <spec-id>`.
> Роль-исполнитель: капитан-оркестратор. С spec 051 STOP-точки A, B и D снимаются
> автоматически при выполнении технических условий (score ≥ 85% ∧ hard-fail 0;
> валидный DAG ∧ max-risk < 50; QC pass ∧ cosine < 0.80 ∧ Haladyna 5/5). Поэтому
> капитан участвует: (1) только когда условие auto **не** выполнено — тогда
> STOP-точка работает как раньше; (2) обязательно в финальном **push** — это
> единственный ручной шаг цепочки (правила 10/11, автономизация push запрещена).
> Файл — reference в репо; рабочая копия появится в
> `~/.dsh/.agent-presets/linuxexam-spec-chain/skills/run-spec-chain/SKILL.md`
> после установки пресета капитаном (операция капитана, вне репо).

## Когда использовать

- Спека лежит в `.project/specs/<id>-<slug>.md` со `status: approved`
  (frontmatter), тип `infra` / `feature` / `content` / `docs`.
- Нужно довести её от черновика до закрытия **одной командой**, без 6–8 раундов
  обмена промптами (spec 040, «Контекст»).
- Прогон идёт в **отдельной сессии DSH**: харнесс не даёт вести две команды
  AgentTeams одновременно (spec 040, Edge Cases).

## Входы

| Вход | Источник |
|---|---|
| `<spec-id>` | аргумент команды, ровно 3 цифры (`040`) |
| спека | `.project/specs/<id>-*.md`, frontmatter `status: approved` |
| контекст фазы | `.project/state.json` → `plan.allPhases` |
| текущий SHA | `git log -1 --format=%H` |
| роли и модели | `~/.dsh/.agent-presets/linuxexam-orchestrator/skills/spec-to-team/roster.yaml` (вне репо); если недоступен — fallback-дефолт ростера из Шага 3 |
| инструменты | `agent_teams_*`, `npm`, `git`, Read / Write / Edit |
| скиллы | `spec-enrich`, `spec-to-team`, `run-spec-chain`; закрытие — CLI `npm run spec:close`, не скилл |

## Предусловия

1. `Test-Path .project/specs/<id>-*.md` → `True`; `status: approved`.
2. `git status` чистый, кроме известных untracked (`.agent-teams/**`).
3. Snapshot гейтов до старта: `npm run typecheck`, `npm run test:run`,
   `npm run sync:check` — записать exit-коды (это baseline, не гейт входа).
4. `agent_teams_status` — сессия не ведёт другую команду (иначе STOP,
   см. «Крайние случаи» → `TEAM-ALREADY-ACTIVE`).
5. Доступен CLI `npm run spec:enrich` (создаётся задачей t4 spec 040).

## Карта цепочки

```
Шаг 0: развилка Small/Fast/Full → Small: 1 builder (kind=work) → spec:close
                                   → Fast:  enrich пропускается → MAS → Playwright → spec:close
                                   → Full:  шаги ниже ↓
Шаг 0.5 (только когда enrich запускается): research → spec-<id>-research.md
enrich → STOP A (auto при score ≥ 85% ∧ hard-fail 0; иначе — approve спеки)
       → /spec-to-team → STOP B (auto при валидном DAG ∧ max-risk < 50; иначе approve плана MAS)
       → исполнение MAS → STOP D (auto при QC pass ∧ cosine < 0.80 ∧ Haladyna 5/5;
                                  иначе approve превью; только type: content)
       → Шаг 4b: Playwright E2E CLI (обязателен для type: feature / ui)
       → запись кандидатов в src/data/** → spec:close → STOP C (отчёт + push-авторизация, всегда вручную)
       → капитан: git push
```

## Маппинг: пункты Компонента B спеки (1–8) → шаги скилла (1–5)

Пункты из spec 040, Компонент B (дословно):

1. `npm run spec:enrich <id>` — 11 фаз.
2. STOP: показать diff и score delta капитану, ждать «ок».
3. `/spec-to-team <id>` — MAS-команда.
4. STOP: показать план MAS-команды капитану, ждать approve.
5. MAS исполняет (builders × N + qc + reviewer).
6. `npm run spec:close -- <id>` — закрытие.
7. STOP: отчёт + ожидание push-авторизации.
8. Капитан → git push.

| Пункт спеки | Содержание пункта | Шаг скилла |
|---|---|---|
| 1 | `npm run spec:enrich <id>` — 11 фаз | Шаг 1 |
| 2 | STOP: diff + score delta, ждать «ок» | Шаг 2 (STOP-точка A) |
| 3 | `/spec-to-team <id>` — MAS-команда | Шаг 3 |
| 4 | STOP: план MAS-команды, ждать approve | Шаг 3 (STOP-точка B) |
| 5 | MAS исполняет (builders × N + qc + reviewer) | Шаг 4 |
| — | STOP: превью вопросов, ждать approve (**только `type: content`**; дополнение правила 6, в пунктах спеки 040 отсутствует) | Шаг 4a (STOP-точка D) |
| — | Playwright E2E-гейт (**обязателен для `type: feature`/`type: ui`**: после MAS и до закрытия спеки, `npm run test:e2e` — CLI, не MCP, `exit 0`; пункта в Компоненте B spec 040 нет) | Шаг 4b |
| 6 | `npm run spec:close -- <id>` — закрытие | Шаг 5 |
| 7 | STOP: отчёт + ожидание push-авторизации | Шаг 5 (STOP-точка C) |
| 8 | Капитан → git push | Шаг 5 — терминальная передача капитану, **агентом не исполняется** |

Покрытие: все 8 пунктов, у каждого ровно один шаг-владелец; плюс два дополнения,
которых в Компоненте B spec 040 нет: STOP-точка D для `type: content` (правило 6)
и обязательный E2E-гейт Шага 4b для `type: feature`/`type: ui`. Пять логических
шагов вмещают четыре STOP-точки (A, B, D, C) и терминальный пункт 8, закреплённый
за капитаном; шаг 4a — подшаг Шага 4 (или самостоятельная остановка сразу после
него), шаг 4b — обязательный подшаг Шага 4 без STOP-точки (гейт `exit 0`, в
отличие от STOP-точек ответа капитана не ждёт).

Дополнения spec 051 (Autonomous Spec Chain, минимальный): Шаг 0.5 (research до
enrich) — подшаг на входе, как и Шаг 0, в пункты spec 040 не входит; auto-условия
трёх STOP-точек (A/B/D) описаны в соответствующих шагах и в сводной таблице.
Логических шагов по-прежнему пять; push (терминальный пункт 8) не автоматизирован.

## Общие правила STOP-точек (A / B / D / C)

- **Таймаут ожидания — 30 мин** (spec 040, Edge Cases). Молчание капитана
  таймаутом **не** считается согласием: по истечении — отчёт и остановка без
  продолжения цепочки.
- **Auto-approve (spec 051).** Точки A, B и D снимаются сами при выполнении
  технических условий из сводной таблицы — это не «молчаливое согласие», а
  измеримое условие прогона, зафиксированное лог-строкой и записью
  `auto-decision` в `.project/DECISIONS.md`. Условие не выполнено — действует
  ручной режим с таймаутом. Точка **C не автоматизируется никогда**: push
  выполняет только капитан.
- Перед STOP печатается сводка (см. таблицу STOP-точек), после — ожидание
  явного ответа. Ответ «revision» / «нет» → правки и повторная STOP-точка,
  не переход дальше.
- Агент не аппрувит за капитана и никогда не выполняет `git push`
  (правила 10/11 — только per-command авторизация).

### Шаг 0 — Классификация Small/Full

**Вход.** Спека `.project/specs/<id>-*.md`, `status: approved`; frontmatter
(`type`); известный состав правок прогона (файлы и дифф); явная формулировка
капитана о треке прогона (для Fast).

**Команда / действие.** Определить трек прогона — **Small**, **Fast** или
**Full**: Small/Full — по таблице порога ниже, Fast — по явной формулировке
капитана (из диффа Fast не выводится). Шаг 0 — **развилка** на входе цепочки, а не
шестой шаг конвейера: логических шагов по-прежнему пять, Шаги 1-5 не
переписываются.

| Граница | Small | Full |
|---|---|---|
| Число файлов | ≤2 файла | 3 файла и больше |
| Число строк (дифф) | ≤50 строк | больше 50 строк |
| Зона | без `src/data/**` | правка `src/data/**` |
| Запрещённые зоны | без правок `.project/sync.mjs`, `.project/contracts/**` и самого `.project/ORCH-RULES.md` | правка `.project/sync.mjs`, `.project/contracts/**` или `.project/ORCH-RULES.md` |
| Тип спеки | без `type:content`, без `type:feature` | `type:content` или `type:feature` |
| Остальное | все границы выше выполнены одновременно | любая невыполненная граница |

**Ветка Small.** `enrich пропускается` (Шаги 1-2 не запускаются). MAS-команда
минимальная: **1 builder**, обе задачи с `kind=work`, ревью — обязательная
вторая задача (то есть минимальный состав — 1 builder, kind=work, ревью —
обязательная вторая задача), закрытие — через CLI закрытия спеки
(`npm run spec:close`). Обязательные STOP-точки при этом не сокращаются.

**Ветка Full.** Цепочка без изменений: Шаги 1-5 — enrich → MAS → закрытие спеки.

**Ветка Fast.** Быстрый капитанский трек (действует **с spec 049**): `enrich`
**пропускается** (Шаги 1-2 не запускаются — требования заданы капитаном полностью),
MAS обязателен, после MAS и **до** закрытия спеки — обязательный прогон Playwright
(`npm run test:e2e`, CLI; не MCP). Условия допуска: тип спеки `infra` или `content`;
требования в задании капитана **явные и полные** (критерии приёмки не требуют
research/enrich); трек называет капитан **явной формулировкой** — агент трек Fast
сам не выбирает и не выводит его из размера диффа. Для `type:content` правило 6
сохраняется: превью и approve капитана (STOP-точка D) остаются обязательными и на
треке Fast. Трек Fast **не выводится из таблицы порога** ниже: таблица
классифицирует Small и Full по диффу и не переписывается. Сама spec 048 идёт
треком **Full** с **пропущенным `enrich`** (прямое решение капитана, трек
`full-enrich-skip`) — трек Fast к ней не применяется.

**Инвариант.** `type:feature` — **всегда Full**, независимо от размера диффа;
`type:content` — **Full или Fast** (правило 6 действует на обоих треках), но **не
Small**.

**Режим отказа (STOP).** Дифф неоднозначен (не хватает данных для оценки файлов
или строк) → трек по догадке не определяется: `трек повышается до Full`, enrich
и полный MAS запускаются, прогон по догадке не продолжается. Если правка вышла
за порог уже в процессе, трек повышается до Full в отчёте прогона. Эскалация
`Small → Fast/Full` и `Fast → Full` разрешена; понижение `Full → Small/Fast`
запрещено.

**Ожидаемый результат.** Выбранный трек записан в отчёт прогона; для Small
перечень задач ограничен минимальной MAS-командой, для Fast — Шаги 1-2 пропущены и
после MAS обязателен прогон Playwright, для Full действуют Шаги 1-5.

**Условие продолжения.** Трек определён и записан в отчёт прогона; для Small и
Fast — план MAS подтверждён на STOP-точке B, для Full — начинается Шаг 1 (enrich).

### Шаг 0.5 — Research-фаза (spec 051, перед enrich)

**Когда применяется.** Всегда, когда Шаг 1 (enrich) вообще запускается: Full-трек и
`full-enrich-skip` — да; Small и Fast (enrich пропущен) — шаг пропускается целиком
вместе с Шагом 1. Порядок обязателен: research **до** enrich, чтобы найденные
практики и риски попали в обогащение, а не после него.

**Вход.** `<spec-id>`; спека `approved`; доступен `.project/scripts/research-spec.mjs`
(`npm run research:spec`); опционально `TAVILY_API_KEY` в окружении.

**Команда / действие.**

```
npm run research:spec -- <id>          # фазы plan → search → reflect → synthesize
npm run research:spec -- <id> --json   # машиночитаемая сводка
```

Фазы: **plan** (3–5 вопросов из цели и критериев спеки) → **search** (веб-поиск, если
есть ключ и сеть; иначе — только репозиторий) → **reflect** (дедуп, ранжирование,
противоречия) → **synthesize** (артефакт + решение).

**Ожидаемый результат.** `.project/drafts/spec-<id>-research.md` с секциями
**Best practices (с URL)** / **Risks** / **Recommendations**; строка решения
«подход X, потому что Y» в `.project/DECISIONS.md` (append-only). При наличии сети —
минимум один http(s)-источник в Best practices.

**Условие продолжения.** `exit 0` (в том числе в repo-only режиме) → Шаг 1.
Артефакт существует и содержит три секции.

**Режим отказа (STOP).** Веб недоступен (нет ключа, 403, таймаут, DNS) → **не STOP**:
WARN `[research: skipped — no network]`, research выполняется только по репозиторию,
цепочка продолжается (spec 051). Артефакт не создан из-за ошибки ввода (спека не
найдена, `exit 2`) → STOP с диагностикой. Research **не отменяет** STOP-точку A:
её условие считается по score/hard-fail Шага 1.

### Шаг 1 — Enrich спеки (11 фаз)

**Вход.** `<spec-id>`; спека `approved`; доступен `npm run spec:enrich`;
записан baseline-отчёт (Предусловия, п. 3).

**Команда / действие.** Скилл `spec-enrich`, Фазы 0–10:

```
npm run spec:enrich <id> --dry-run   # опционально: печать 11 фаз + baseline score, ноль правок
npm run spec:enrich <id>             # apply: правки спеки + отчёт (score до/после, diff, findings)
```

Правки Фазы 9 делаются только в файле спеки `.project/specs/<id>-*.md`; код,
тесты и `package.json` на этом шаге не трогаются.

**Ожидаемый результат.** Пройдены 11 фаз; собраны: score до/после, `diff`
правок спеки, findings со severity и confidence, tiered sources (Tier 1–2),
traceability Цель → Критерий → Задача. Изменённая спека содержит хотя бы один
маркер `[enriched: URL|tier|дата]`.

**Условие продолжения.** `spec:enrich` завершился с `exit 0`, и либо score
delta > 0, либо вердикт «clean» (0 hard-fail + 0 high-finding → правки не
требуются). Отчёт и diff сформированы для показа капитану на Шаге 2.

**Режим отказа (STOP).** Hard-fail (сироты traceability, spec gaming,
изменение intent) → STOP, rollback правок Фазы 9, отчёт капитану; Шаг 2 не
начинать. Repair loop не сошёлся за 3 итерации (score не растёт) → STOP без
продолжения. `exit != 0` либо CLI `spec:enrich` не найден (`npm` сообщает
missing script) → STOP с диагностикой; альтернативный путь — выполнить скилл
`spec-enrich` вручную, но без отчёта и score delta цепочка не продолжается.

### Шаг 2 — STOP-точка A: approve обогащённой спеки

**Вход.** Отчёт Шага 1: `diff` правок спеки, score до/после, findings,
tiered sources, список правок Фазы 9.

**Авто-режим (spec 051).** Перед сводкой берётся решение, которое `spec:enrich`
печатает сам: если прогон завершился `exit 0` ∧ score ≥ 85% от weightSum ∧
hard-fail findings = 0, STOP-точка A **снимается автоматически** — печатается лог
`auto-approve STOP A | score:N | hard-fail:0`, скрипт `enrich-spec.mjs` дописывает в
`.project/DECISIONS.md` строку
`YYYY-MM-DD | auto-decision | STOP A | spec-<id> | reason:<условия>`, и цепочка идёт
на Шаг 3 **без ожидания капитана**. Уведомление капитану всё равно отправляется
(fire-and-forget), но ответа не ждём. Если условие не выполнено (score < 85%,
hard-fail > 0 либо `exit != 0`) — действует прежний ручной режим ниже, включая
таймаут 30 мин.

**Команда / действие.** Сводка капитану (без мутаций) и ожидание явного «ок».

Перед сводкой — уведомление о STOP-точке (fire-and-forget, сбой Telegram не
мешает цепочке):

```
npm run notify -- "⏳ Спека <id>: STOP A — обогащённая спека готова. Жду твоё решение." --event stop_point
```

Сводка:

```
## STOP A — обогащённая спека <id>
score: <до> → <после>  (delta <+N>)
findings: hard-fail <n> | high <n> | medium <n> | low <n>
правки Фазы 9: <n> (см. diff ниже)
tiered sources: Tier 1 <n>, Tier 2 <n>
открытые вопросы: <n>
ЖДУ: «ок» / «revision: <что поменять>»   (таймаут 30 мин)
```

**Ожидаемый результат.** Получен явный approve капитана («ок» / «approve»)
либо конкретный список правок. Спека с approve фиксируется как baseline
исполнения (сохранить SHA-подобный отпечаток: дату, score, число правок —
для отчёта Шага 5).

**Условие продолжения.** Только явное «ок» → Шаг 3. Ответ «revision» → правки
(Фаза 9), повторный показ diff и повторная STOP-точка A.

**Режим отказа (STOP).** Таймаут 30 мин без ответа → отчёт капитану и
остановка, Шаг 3 не начинать. Hard-fail, не снятый правками → STOP без
продолжения. Enrich не выполнен (нет отчёта/score) → STOP с сообщением
«enrich не выполнен». Агент не подменяет approve собственным решением.

### Шаг 3 — /spec-to-team: план MAS + STOP-точка B

**Вход.** Approve Шага 2; спека `approved`; ростер ролей и моделей (см. блок
ниже); snapshot гейтов.

**Источник ролей и моделей (устранение F4).** Ростер читается по фактическому
пути пресета-владельца скилла `spec-to-team` — он лежит **вне репозитория**:

```
Test-Path ~/.dsh/.agent-presets/linuxexam-orchestrator/skills/spec-to-team/roster.yaml
# → True: файл существует в этом окружении (35 строк, provider deepseek-official)
```

Если путь недоступен (пресет не установлен, другая машина), используется
самодостаточный **fallback-дефолт** ниже; импровизация в выборе моделей
запрещена — план на STOP-точке B обязан содержать роли и модели из одного из
двух источников:

| Роль | provider | model | reasoning_effort |
|---|---|---|---|
| architect | deepseek-official | deepseek-v4-pro | high |
| builder | deepseek-official | deepseek-v4-flash | high |
| tester | deepseek-official | deepseek-v4-flash | high |
| reviewer | deepseek-official | deepseek-v4-pro | high |
| writer (content) | deepseek-official | deepseek-v4-flash | high |
| qc (content) | deepseek-official | deepseek-v4-pro | high |

Допустимые уровни `reasoning_effort` — `off` / `low` / `high` / `max`
(`medium` для pro не поддерживается). Состав ролей по `type` спеки:
infra/feature → architect, builder, tester, reviewer; content → writer, qc;
docs → writer, reviewer; мелкая правка (1 файл) → builder + reviewer. Любая
иная комбинация ролей или моделей — только с approve капитана на STOP-точке B.

**Команда / действие.** Порядок разделён, чтобы STOP B стоял **до** старта
исполнения (пункт 3 спеки ≠ разрешение запускать без approve пункта 4):

1. Фазы 1–4 скилла `spec-to-team`: прочитать спеку (Цель, Что делаем,
   Критерии, Что НЕ трогать, type), выбрать роли по ростеру из блока выше
   (фактический путь пресета или fallback-дефолт; состав по типу:
   infra/feature → architect, builder, tester, reviewer; content → writer, qc;
   docs → writer, reviewer), разложить задачи (при наличии `## Декомпозиция` —
   по ней), провалидировать DAG: зависимости на существующие id, нет циклов,
   write-скоупы не пересекаются.
2. `agent_teams_status` — проверка, что сессия не ведёт другую команду.
3. **Авто-условие STOP B (spec 051).** Взять из плана прогона `maxRiskScore` и
   `dag.valid` (их печатает `run-spec.mjs`: `план.tasks[].risk_score`,
   `план.maxRiskScore`, `план.riskDecision`, `план.stopB`). Если DAG валиден **и**
   `max_risk_score < 50` (`AUTO_THRESHOLD`), STOP-точка B снимается автоматически:
   печатается лог `auto-approve STOP B | DAG valid | max-risk:N`, в
   `.project/DECISIONS.md` добавляется строка
   `YYYY-MM-DD | auto-decision | STOP B | spec-<id> | reason:<условия>`, и сразу
   выполняется `agent_teams_create` (пункт 5) без ожидания капитана. При
   `max_risk_score ≥ 50` — в том числе любая задача с `git push` в actions (вес 80,
   `HUMAN_THRESHOLD`) — или невалидном DAG работает ручной режим пункта 4.
4. **STOP B (ручной режим)**: перед показом плана уведомить капитана —
   `npm run notify -- "⏳ Спека <id>: STOP B — план прогона готов. Жду твоё согласие." --event stop_point` —
   затем показать капитану план MAS — `team_id`-кандидат, роли/модели,
   список задач с assignee, dependencies, write-скоупами, kinds, evidence
   и риск-оценку (`risk_score` каждой задачи, `max-risk`).
   Ждать явный approve.
5. После approve (пункт 4) либо при авто-условии (пункт 3) — `agent_teams_create`
   (фаза 5 скилла `spec-to-team`).

**Ожидаемый результат.** Явный approve плана; команда создана, получен
`team_id`, задачи выданы членам, зависимости разблокированы планировщиком.
Наружу отдан план из таблицы (роль → задача → зависимости → write-скоуп).

**Условие продолжения.** Approve плана получен, `agent_teams_create` вернул
успех, `agent_teams_status` показывает задачи в `dispatched`/`in_progress` →
Шаг 4.

**Режим отказа (STOP).** Нет approve или капитан меняет план → пересобрать
план и снова STOP B. `agent_teams_status` видит активную команду → STOP:
`TEAM-ALREADY-ACTIVE: сессия ведёт команду <id>. Требуется новая сессия DSH,
чтобы запустить новый spec-прогон. Харнесс не даёт вести две команды
одновременно.` Чужую команду не завершать (`agent_teams_delete` запрещён) и не
переиспользовать. Инструменты `agent_teams_*` недоступны в сессии → STOP с
диагностикой (имя инструмента, текст ошибки, что нужно: новая сессия DSH /
установленный пресет). `agent_teams_create` упал → одна повторная попытка,
затем STOP с диагностикой. Таймаут 30 мин на STOP B → отчёт и остановка.

### Шаг 4 — Исполнение MAS-команды

**Вход.** Созданная команда (`team_id`), approved план, задачи с зависимостями
и write-скоупами.

**Команда / действие.** Наблюдение и координация (работу делают члены команды,
не оркестратор):

```
agent_teams_status              # каждые 15 с, максимум 50 итераций за окно (12.5 мин)
agent_teams_send_message        # при простое/вопросе — адресно члену команды
```

`wait_agent` members AgentTeams не видит — использовать только
`agent_teams_status`. Разрешено: уточнять задачу члену, эскалировать
блокеры капитану. Запрещено: править файлы за членов команды, reassign,
claim чужих задач, создавать/удалять команду.

**Ожидаемый результат.** Все задачи в терминальном статусе; собраны
`tasks[].output`, `changedPaths`, `acceptanceResults`, `commandsRun`,
`verdict` ревьюера; гейты прогона (`typecheck`, `test:run`, `sync:check`)
и evidence по критериям приёмки спеки.

**Условие продолжения.** Все задачи `completed` (допускаются `cancelled` с
обоснованием) **и** reviewer `verdict=pass` → Шаг 5 (для `type: content` — через
STOP-точку D, Шаг 4a). Иначе Шаг 5 не начинать.

**Режим отказа (STOP).** Задача `failed` либо reviewer вернул
`needs_revision`/`reject` → STOP: отчёт капитану с findings, закрытие не
запускать (правки — новой задачей или новым прогоном). Инструменты
`agent_teams_*` недоступны → STOP с диагностикой. Два окна поллинга подряд без
изменений статуса → отчёт и STOP (чужую команду не завершать). Всегда
действует запрет push (правила 10/11).

### Шаг 4a — STOP-точка D: approve превью вопросов (`type: content`)

**Когда применяется.** Только для спек `type: content`. Для `infra` / `feature` /
`docs` этот шаг пропускается целиком: по завершении Шага 4 цепочка идёт прямо
в Шаг 5. STOP D существует потому, что правило 2 (approved spec = авторизация
исполнения) **не** распространяется на контент банка: правило 6 (редакция
2026-09-28) требует approve капитана на превью, и превью обязано быть показано
**до** попадания вопросов в `src/data/**` (DOD: демонстрация артефакта до коммита).

**Вход.** Прогон MAS завершён (Шаг 4: все задачи терминальные, reviewer/qc
`verdict=pass`); превью-артефакт спеки существует — `.project/drafts/<batch>-preview.md`
(полный текст кандидатов + таблица метрик `id` / ratio (chars) / порог класса /
max cos / ближайший сосед / Haladyna + риски). Кандидаты **ещё не записаны**
в `src/data/questions/*.json`.

**Команда / действие.** Сводка капитану (без мутаций) и ожидание явного approve.

**Авто-режим (spec 051).** Если QC-вердикт = `pass` ∧ максимальный cosine против
банка < 0.80 ∧ Haladyna AUTO 5/5 (и SEMI 3/3) — STOP-точка D **снимается
автоматически**: печатается лог `auto-approve STOP D | QC:pass | cosine:N`
(N — максимум по батчу), в `.project/DECISIONS.md` добавляется строка
`YYYY-MM-DD | auto-decision | STOP D | spec-<id> | reason:<условия>`, и кандидаты
сразу записываются в `src/data/**` (интеграция). Вариант QC — **A: один QC (pro)**;
consensus-модели (QC pro ∧ QC flash) областью spec 051 запрещены. Если условие не
выполнено (QC ≠ pass, cosine ≥ 0.80, Haladyna < 5/5) — действует ручной режим ниже,
включая таймаут 30 мин: вопросы в `src/data/**` не пишутся, `feat`-коммит не делается.

Перед сводкой — уведомление о STOP-точке (fire-and-forget, сбой Telegram не мешает
цепочке):

```
npm run notify -- "⏳ Спека <id>: STOP-точка D — превью вопросов готово. Жду твоё решение." --event stop_point
```

Сводка:

```
## STOP D — превью вопросов спеки <id> (type: content)
превью: .project/drafts/<batch>-preview.md (что в нём: тексты + таблица метрик + риски)
кандидатов: <n> (accept <n> / reject <n>)
cosine против банка: max <значение> (ближайший сосед <id>~<id>), пар > 0.80 внутри батча <n>
Haladyna: AUTO 5/5 и SEMI 3/3 у <n> из <n>; ratio вне порога класса: <n>
в банк ещё не записано: src/data/** не изменялся, feat-коммит не сделан
ЖДУ: «ок» / «revision: <что поменять>»   (таймаут 30 мин)
```

**Ожидаемый результат.** Явный approve капитана («ок» / «approve») либо конкретный
список правок к кандидатам. Превью с approve фиксируется как baseline интеграции
(дата, число кандидатов, метрики — для отчёта Шага 5).

**Условие продолжения.** Только явное «ок» → запись кандидатов в `src/data/**`
(и далее Шаг 5). Ответ «revision» → правки кандидатов новой итерацией, обновлённое
превью и **повторная** STOP-точка D; интеграция не начинается.

**Режим отказа (STOP).** Нет approve (в том числе таймаут 30 мин) → отчёт капитану
и остановка: вопросы в `src/data/**` не пишутся, `feat`-коммит не делается,
`spec:close` не запускается. Правки в уже интегрированный банк вместо новой
итерации кандидатов запрещены. Агент не аппрувит за капитана и не трактует
молчание как согласие; push не выполняется (правила 10/11).

### Шаг 4b — Playwright E2E (обязателен для type: feature / type: ui)

**Когда применяется.** Для спек `type: feature` и `type: ui` — **обязательно**:
подшаг исполняется после завершения MAS (Шаг 4, включая Шаг 4a, если он был) и
**до** Шага 5 (`npm run spec:close`). Для `type: infra` / `content` / `docs` шаг
пропускается. Пропуск Шага 4b для `feature`/`ui` — не «оптимизация», а нарушение
гейта: без него спека закрывается без единого E2E-прогона.

**Инструмент — только Playwright CLI.** Гейту нужен воспроизводимый exit-код и
артефакт прогона в репозитории; **Playwright MCP запрещён**: MCP-сессия не
оставляет ни того, ни другого в evidence, прогон через MCP гейт не закрывает.

**Вход.** Прогон MAS завершён (Шаг 4: все задачи терминальные, reviewer
`verdict=pass`); тип спеки `feature`/`ui`; существующий набор `e2e/**` (новых
E2E-тестов не пишем — состав `e2e/` не меняется); chromium-only (`AGENTS.md`).

**Команда / действие.**

```
npx playwright install chromium   # предусловие: chromium-only (AGENTS.md)
npm run test:e2e                  # Playwright CLI, не MCP
```

**Ожидаемый результат.** `npm run test:e2e` → `exit 0`. Evidence: exit-код прогона
и артефакты прогона в репозитории (`test-results/**`, отчёт Playwright).

**Условие продолжения.** `npm run test:e2e` → `exit 0` → Шаг 5. `exit != 0` → STOP,
Шаг 5 не начинать.

**Режим отказа (STOP).** `npm run test:e2e` → `exit != 0` → STOP: отчёт с выводом
прогона, Шаг 5 не начинать, закрытие спеки не запускать (правки — новой задачей,
прогон повторяется целиком). `npx playwright install chromium` не проходит (нет
сети/зеркала) → STOP с диагностикой (команда + текст ошибки); гейт **не**
подменяется MCP-прогоном. Прогон объявлен «зелёным» без артефактов в репозитории
→ evidence недостаточно, STOP.

### Шаг 5 — npm run spec:close + STOP-точка C: отчёт и push-авторизация

**Вход.** Прогон MAS завершён с reviewer `verdict=pass`; спека `approved`;
известны `team_id`, токены задач (id completed), файлы и гейты прогона.

**Команда / действие.**

```
npm run spec:close -- <id> --dry-run   # сначала dry-run: план шагов закрытия, ноль мутаций
npm run spec:close -- <id>             # apply: status done + R5-trace + память + commit-chain + sync:check
```

После apply — уведомить капитана о STOP-точке (fire-and-forget):

```
npm run notify -- "ℹ️ Спека <id>: STOP C — отчёт готов. Жду разрешение на публикацию." --event stop_point
```

Затем собрать отчёт и **STOP C**: показать капитану отчёт и список
коммитов, затем ждать push-авторизацию. Push выполняет **только капитан**
(правила 10/11); агент не пушит ни после approve, ни по таймауту.

**Ожидаемый результат.** `status: done` в frontmatter спеки, R5-trace,
запись в `docs/memory/episodic.md` (+ обновлённый `working.md`), commit-chain
(`docs(spec-<id>): done` → converge), `npm run sync:check` → `exit 0`.
Отчёт: `team_id`, задачи, verdict, `changedPaths`, гейты, score delta
Шага 1, список коммитов.

**Условие продолжения.** Отчёт показан капитану. Цепочка завершена после явной
**отдельной** push-авторизации капитана — она не входит в процесс агента и не
является частью этого скилла; терминальный пункт 8 спеки исполняет капитан.

**Режим отказа (STOP).** `spec:close` вернул `exit 2` (STOP скрипта: status не
`approved`, нет reviewer-`pass`, нет команды) или `exit 3`
(precondition-missing) → закрытие не применять, отчёт и STOP. `sync:check != 0`
после converge → STOP с выводом гейта (правило 9, без отката). Таймаут 30 мин
без ответа капитана → отчёт и остановка; push не выполняется. Маркер
`MEMORY-WRITE-FAILED` (запись в `episodic.md` не подтверждена
`git status --porcelain`) → отчёт и STOP.

|---|---|
| enrich не выполнен (нет отчёта/score delta) | STOP с сообщением «enrich не выполнен»; Шаг 2 не начинать |
| активная MAS-команда в сессии | STOP: `TEAM-ALREADY-ACTIVE: ... требуется новая сессия DSH`; чужую команду не завершать и не переиспользовать |
| инструменты `agent_teams_*` недоступны | STOP с диагностикой: имя инструмента, текст ошибки, что нужно (новая сессия DSH / установленный пресет) |
| ростер недоступен по пути пресета (`Test-Path` → `False`) | не STOP: взять fallback-дефолт ростера из Шага 3 (роли + модели + reasoning_effort) и пометить это в плане на STOP-точке B |
| капитан не отвечает на STOP-точку | таймаут 30 мин → отчёт, остановка, не продолжать |
| нет approve STOP D (или ответ «revision») для `type: content` | вопросы в `src/data/**` не пишутся, `feat`-коммит не делается, `spec:close` не запускается; правки — новой итерацией кандидатов (не правкой уже интегрированного банка) |
| research без сети (Фаза 2) | не блокер цепочки: Фаза 2 пропускается с WARN `[research: skipped — no network]`, score не уменьшается |

| источник противоречит спеке | не разрешать самому: вынести в «Открытые вопросы» и показать в STOP A |

| неоднозначная классификация Small/Full (Шаг 0) | трек повышается до Full: enrich и полный MAS запускаются; по догадке прогон не продолжается |
| `type: feature`/`ui` без Playwright-прогона | закрытие запрещено: Шаг 4b обязателен, его пропуск — нарушение гейта, а не «оптимизация» |

| прогон E2E объявлен «зелёным» без артефактов в репозитории | evidence недостаточно: нужны exit-код и `test-results/**`; STOP |

## Что не делать

- **Не пушить** (правила 10/11 — только per-command авторизация капитана).
- **Не считать auto-approve разрешением на push**: авто-снятие STOP-точек A/B/D
  (spec 051) не распространяется на точку C — push всегда отдельная
  per-command авторизация; автоматизация push вне области цепочки.
- **Не выводить auto-условия «на глазок»**: score/hard-fail берутся из отчёта
  `spec:enrich` (`auto-approve STOP A | score:N | hard-fail:0`), риск — из
  `plan.maxRiskScore` / `plan.stopB` (`run-spec.mjs`), метрики превью — из таблицы
  превью (QC / cosine / Haladyna). Условие не выполнено → STOP-точка ручная.
- **Не добавлять вне области spec 051**: hash-chain audit, external watchdog,
  consensus-модели QC (вариант «QC pro ∧ QC flash»), graduated halt modes —
  вариант QC здесь один: **один QC (pro)**.
- Не аппрувить за капитана: молчание STOP-точки не является согласием.
- **Не писать вопросы в `src/data/**` для `type: content` без явного approve
  STOP-точки D** (правило 6): прогон MAS может подготовить кандидатов и превью,
  но запись в банк и `feat`-коммит — только после approve капитана.
- Не завершать и не переиспользовать чужую MAS-команду (`agent_teams_delete`
  агенту запрещён); не переиспользовать evidence предыдущего прогона.
- Не править файлы вне `inScope` спеки и не выполнять работу членов команды
  вместо них.
- Не устанавливать пресет/плагины: `~/.dsh/.agent-presets/**` — операция
  капитана; агент создаёт только документацию и reference-копии скиллов в репо.
- **Не подменять E2E-гейт Playwright MCP**: для `type: feature`/`type: ui`
  обязателен Playwright **CLI** (`npx playwright install chromium` +
  `npm run test:e2e`) — нужен воспроизводимый exit-код и артефакт прогона в
  репозитории (`test-results/**`); MCP-сессия evidence не создаёт.
- **Не закрывать спеку `type: feature`/`type: ui` без Шага 4b** (`npm run test:e2e`
  → `exit 0`) и не переносить E2E-прогон после `spec:close`: подшаг стоит после MAS
  и до закрытия спеки.
- Не запускать subagent'ов параллельно с командой AgentTeams.

## Критерий приёмки прогона

- infra / feature: все гейты зелёные + reviewer `verdict=pass` + approve
  капитана.
- `type: feature` / `type: ui` — дополнительно **Шаг 4b**: Playwright CLI-прогон
  `npm run test:e2e` → `exit 0` **после MAS и до** `spec:close`, с артефактами
  прогона `test-results/**`; пропуск подшага или прогон вместо CLI (MCP) → прогон
  не принимается, закрытие запрещено.
- content: QC `verdict=pass` + **approve превью на STOP-точке D** + approve
  капитана.
- Запись в `docs/memory/episodic.md` есть (эвиденс: `git status --porcelain`
  показывает `M docs/memory/episodic.md`).
- Push — отдельная авторизация капитана (правила 10/11); без неё прогон
  считается завершённым на STOP-точке C.
