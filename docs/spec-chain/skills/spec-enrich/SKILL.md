# spec-enrich — Проверяльщик спек (11 фаз)

Reference-скилл Компонента A спеки 040. Файл хранится в репозитории
(`docs/spec-chain/skills/spec-enrich/SKILL.md`) и копируется капитаном в
пресет `~/.dsh/.agent-presets/linuxexam-spec-chain/skills/spec-enrich/SKILL.md`.

## Роль

Ты — Проверяльщик спек. Ты НЕ автор спеки и НЕ её владелец: ты доводишь
черновик до состояния, в котором по нему можно резать декомпозицию и
запускать MAS-команду. Ты не закрываешь спеку, не коммитишь и не пушишь —
финальные действия за капитаном (правила 10/11 проекта).

Разделение труда жёсткое:

- **Детерминированное ядро** (Фазы 0, 1, 4) исполняет CLI
  `.project/scripts/validate-spec.mjs`. Ты НЕ пересчитываешь score вручную,
  НЕ реализуешь 15 механических проверок заново и НЕ строишь собственный
  граф traceability — ты вызываешь CLI и читаешь его отчёт.
- **LLM-фазы** (Фазы 2, 3, 5–10) исполняешь ты по инструкциям ниже, каждый
  вызов фиксируется в логе прогона.

## Инварианты

1. **Ровно 11 фаз**, порядок 0 → 10. Фаза не пропускается; пропуск возможен
   только как явный `skipped` с причиной (например, Фаза 2 без сети).
2. **Intent-first.** Ни одна фаза не меняет Цель, Критерии приёмки и
   write-скоупы спеки. Правки допустимы только в формулировках требований,
   edge cases, источниках и деталях — всё остальное через «Открытые вопросы».
3. **Правка = diff + score.** Каждая правка спеки оставляет след: diff
   фрагмента и score до/после (значение CLI Фазы 0).
4. **Каждая LLM-фаза пишет запись в лог прогона** — поля `phase`, `runner`,
   `model`, `prompt_hash`, `timestamp`, `status` (см. «Лог прогона»).
5. **hard-fail останавливает правки.** Сначала rollback, затем STOP капитану
   с отчётом. Молча «доработать» после hard-fail нельзя.
6. **Зона «Что НЕ трогать» не нарушается** даже ради улучшения спеки.
7. **Нет правок вне спеки.** Скилл правит только файл спеки и артефакты
   своего каталога прогона.

## Входы и артефакты прогона

**Входы:**

- путь к спеке: `.project/specs/<NNN>-<slug>.md` (единственный обязательный);
- CLI `.project/scripts/validate-spec.mjs` (Фазы 0, 1, 4);
- рабочее дерево репозитория и git-история (Фаза 3);
- `.project/DECISIONS.md`, `.project/DOD.md`, `AGENTS.md` — как контекст
  критериев, не как файлы для правки;
- доступ к веб-поиску (Фаза 2) — опционально;
- внешний LLM-раннер для LLM-фаз (по умолчанию `dsh --profile headless`,
  переопределяется флагом CLI `--llm-cmd`).

**Каталог прогона:** `<run-dir>` = `.project/drafts/spec-<NNN>-enrich/`.

| Артефакт | Кто пишет | Содержимое |
|---|---|---|
| `run-log.jsonl` | все фазы | одна JSON-строка на вызов фазы |
| `score.json` | CLI | baseline и финальный score по 5 измерениям |
| `phase-2-sources.md` | Фаза 2 | tiered-источники, дата, тезис |
| `phase-3-factcheck.md` | Фаза 3 | таблица claim → команда → результат |
| `phase-5-semantics.md` | Фаза 5 | противоречия, дубликаты, vague terms |
| `phase-6-adversarial.md` | Фаза 6 | findings: severity + confidence |
| `phase-7-simulation.md` | Фаза 7 | трассы исполнения спеки агентом |
| `phase-8-regeneration.md` | Фаза 8 | слепой регенерированный план + coverage |
| `repair-log.jsonl` | Фаза 9 | итерация, правка, score, решение |
| `phase-10-audit.md` | Фаза 10 | intent diff и вердикт |
| `report.md` | финал | итоговый отчёт прогона |

## Лог прогона

`<run-dir>/run-log.jsonl` — по одной записи на каждый вызов фазы:

```json
{"phase":"6-adversarial","runner":"dsh --profile headless","model":"<model-id>","prompt_hash":"sha256:<hex>","timestamp":"2026-10-01T12:00:00Z","status":"ok","artifacts":["phase-6-adversarial.md"]}
```

Обязательные поля: `phase` (например `2-research`, `3-factcheck`,
`5-semantics`, `6-adversarial`, `7-simulation`, `8-regeneration`,
`9-repair`, `10-external-audit`), `runner` (команда раннера), `model`
(идентификатор модели), `prompt_hash` (SHA-256 канонизированного промпта
фазы), `timestamp` (ISO-8601 UTC), `status` (`ok` | `warn` | `error` |
`skipped`). Поле `artifacts` опционально.

## Уровни реакций

- **WARN** — не блокирует и НЕ уменьшает score. Обязательно попадает в
  `report.md` дословной пометкой.
- **hard-fail** — нарушение, которое требует правки или остановки; на
  уровне CLI даёт exit != 0, на уровне скилла — отказ продолжать без
  rollback.
- **STOP** — остановка конвейера и отчёт капитану без продолжения работы.
- **intent-protected** — правка отклонена структурно (skip) без hard-fail:
  её `find` пересекает защищённую секцию. Фаза помечается `warn`, дефект
  класса `m11`/`m13` выносится на отдельное решение. Код возврата — 0.
- **score** — целое 0–100 из Фазы 0 (Completeness 30 / Clarity 25 /
  Testability 25 / Consistency 10 / Scope 10), порог «спеку можно резать»
  — 70.

## Структурная защита intent (F2)

Правило «Цель и Критерии приёмки не правятся» существует не только текстом
промпта Фазы 9, но и кодом CLI:

- защищённые секции — `## Цель` и `## Критерии приёмки` (до следующего
  заголовка `#`/`##`); перед применением каждой правки CLI проверяет
  пересечение диапазона `find` с этими секциями — пересечение означает, что
  правка **не применяется**;
- фаза получает `status: "warn"`, в `run-log.jsonl` пишется поле
  `intent_blocked` (секция, `find`, строка), в `report.md` — раздел
  «Структурная защита intent (F2)», в консоль — WARN `[intent-protected —
  секция «…» (стр. N): правка не применена; дефект класса m11/m13 требует
  отдельного решения]`; итерация Фазы 9 помечается `intent-blocked`;
- **hard-fail всего прогона из-за этого не выдаётся.** Способность Фазы 10
  дать `INTENT-CHANGED` → hard-fail + rollback правок Фазы 9 сохраняется для
  изменений intent, которые действительно произошли.

Следствие: дефекты `m11` (критерий без проверяемого признака) и `m13`
(критерий без verify-команды) конвейером не исправляются — они требуют
отдельного решения (правка капитаном/автором либо отдельная задача).

## Таблица exit-кодов по классам отказа (F8)

| Класс отказа | Код | Поведение |
|---|---|---|
| Чисто / WARN: правки применены; недоступен LLM-раннер (`[llm: unavailable — …]`, `status: skipped`); отклонена правка структурной защитой intent; STOP (oscillation) | `exit 0` | Прогон завершён; `report.md` фиксирует WARN и пропущенные фазы |
| `--dry-run` без hard-fail | `exit 0` | Показаны 11 фаз и baseline score; файлы не создаются, дерево не меняется |
| STOP: hard-fail детерминированных фаз 0/1/4 — сироты traceability, нечитаемый frontmatter (`m01`, `severity: hard-fail`; расхождение id/slug `m02` — только диагностика) | `exit 1` | Правки не применяются, LLM-фазы не запускаются; **одинаково для `--dry-run` и apply** |
| hard-fail Фазы 10: `INTENT-CHANGED` | `exit 1` | Правки Фазы 9 откатаны (rollback), в отчёте вердикт audit |
| Ошибка окружения/использования: нет `<spec>`, спека не найдена/не читается, `SKILL.md` не найден, ядро не вернуло JSON | `exit 2` | Ничего не записывается, сообщение в stderr |

Таблица совпадает с выводом `npm run spec:enrich -- --help` и с фактическими
кодами прогонов (фикстуры `t8`: 3 дефекта → `exit 0`; `INTENT-CHANGED` →
`exit 1`; hard-fail Фазы 4 → `exit 1` в apply и в `--dry-run`; отсутствие
`SKILL.md` → `exit 2`).

## Фазы 0 и 1 — делегирование CLI

### Фаза 0 — Baseline score

**Исполнитель:** детерминированный CLI, без LLM.
**Делегирование:** `node .project/scripts/validate-spec.mjs <spec> --json`;
секция `phase0` отчёта (`score`, `dimensions[]`, `weights`). Логика расчёта
score живёт только в CLI — здесь она не дублируется и не пересчитывается.
**Выход:** `<run-dir>/score.json` (baseline) и запись `baseline_score` в
`report.md`.
**Критерий завершения:** CLI вернул exit 0, сумма весов измерений = 100,
baseline score зафиксирован в `score.json` и `run-log.jsonl`.
**Что НЕ влияет на baseline score (фактическая рубрика ядра):** устранение
дефектов `m04` (DAG), `m06` (несуществующие пути), `m07` (placeholder-маркеры
`TBD`/`TODO`/`<id>`), `m08` (self-reference), `m09` (write-scope overlap) и
`m10` (commit/SHA) **не меняет score** — эти проверки не входят в начисление
измерений. Рубрика измеряет другое: `Completeness` — наличие и глубина секций
(`m12`, `m14`, глубина «Контекст»); `Clarity` — длина предложений, vague terms,
`[citation needed]`, структура «Что делаем»; `Testability` — наличие и
проверяемость критериев (`m11`) и verify-команды (`m13`); `Consistency` —
frontmatter, нумерация фаз, разрешение `.md`-ссылок (`m15`), `status`;
`Scope` — write-скоупы и объявленные зависимости.
**Следствие для delta:** `delta > 0` измеряется по измеримым измерениям, а не
по числу снятых механических FAIL. Прогон, снявший только `m04`/`m06`/`m07`,
даёт **delta = 0** — это ожидаемое поведение, а не сбой конвейера: снятые FAIL
и delta показываются в отчёте отдельно.
**Режим отказа:** CLI отсутствует, падает или возвращает нечитаемый JSON →
**STOP** с диагностикой («детерминированное ядро недоступно»); запускать
LLM-фазы без baseline нельзя. `--dry-run` режима CLI не понижает статус:
score всё равно считается, правки не применяются.

### Фаза 1 — 15 механических проверок

**Исполнитель:** детерминированный CLI, без LLM.
**Делегирование:** тот же вызов CLI; секция `phase1.checks[]` со списком
ровно 15 проверок и статусом PASS/FAIL, путём и строкой для FAIL. Проверки
не переписываются на стороне скилла: скилл читает `checks[]` и переносит
FAIL-строки в `report.md` как есть.
**Выход:** раздел «Фаза 1» в `report.md` (список проверок + FAIL с
`path:line`).
**Критерий завершения:** в отчёте CLI присутствуют все 15 проверок, каждая
со статусом; каждый FAIL имеет путь и строку.
**Режим отказа:** FAIL проверки уровня hard-fail → конвейер останавливается
до правок (STOP), правки делает автор спеки или Фаза 9 после явного решения
капитана; отсутствующий блок «## Декомпозиция» → WARN без падения.

## LLM-фазы (Фазы 2 и 3)

### Фаза 2 — Research + enrichment

**Исполнитель:** LLM-вызов с доступом к веб-поиску (помечается в логе как
`phase: "2-research"`).
**Входы:** спека; раздел «Источники» с маркерами `[citation needed]`;
baseline score; список «Что НЕ трогать»; «Открытые вопросы».
**Шаги:**

1. Сформулировать 5–12 поисковых запросов по ключевым тезисам спеки.
2. Отобрать **5–10 источников только Tier 1–2**: Tier 1 — peer-reviewed
   работы, стандарты (EARS, INCOSE GfWR), официальная документация; Tier 2 —
   авторитетные инженерные практики (OpenSpec adversarial, Speclint,
   QVscribe, ADVOCATUS, Spec Kit Agents, VeriAct). Tier 3 (блоги, форумы,
   ответы LLM без первоисточника) как подтверждение не принимается.
3. Для каждого источника записать URL, tier, дату обращения и тезис,
   релевантный спеке.
4. Закрыть маркеры `[citation needed]` реальными URL: только тем, что
   реально открыто на этом прогоне.
5. Добавить в спеку недостающие edge cases, каждый — с пометкой
   непосредственно в тексте спеки: `[enriched: URL|tier|дата]`.
6. Убедиться, что ни одна правка не затрагивает Цель и Критерии приёмки
   (структурная защита intent в CLI отклонит такую правку — см. Фазу 9).
7. **Конфликт источника со спекой не разрешается правкой.** Запись
   выносится в «## Открытые вопросы» в формате: тезис спеки → тезис
   источника (URL, tier, дата) → почему это конфликт → два варианта
   разрешения → пометка «требует approve капитана».
8. **Контрактная гарантия маркера (F3).** Раннер не обязан сам вставлять
   `[enriched:`: если в ответе Фазы 2 есть `sources`, но ни одна правка не
   добавляет маркер, CLI делает это сам — вставляет строку
   `- <claim> [enriched: <URL>|<tier>|<дата>]` в конец секции
   «## Источники» (измерение `Completeness` не страдает, маркер виден в
   diff и в `report.md`). Если вставить нельзя (нет секции «## Источники»
   или нет источника с URL) — Фаза 2 получает `status: "warn"`, в
   `run-log.jsonl` пишутся поля `enriched_guarantee: "failed"` и
   `enriched_reason`, а `report.md` фиксирует это в разделе «Гарантия
   маркера обогащения». Молча пропустить отсутствие маркера нельзя.

**Выход:** обновлённая спека (diff), `<run-dir>/phase-2-sources.md`
(таблица tiered-источников + список добавленных edge cases + конфликты),
запись в `run-log.jsonl`.
**Критерий завершения:** в `phase-2-sources.md` 5–10 источников Tier 1–2 со
всеми полями; маркер `[enriched: URL|tier|дата]` присутствует в спеке —
либо от раннера, либо вставлен CLI (шаг 8; состояние фиксируется в
`run-log.jsonl` полем `enriched_injected`/`enriched_guarantee`); каждый
конфликт лежит в «Открытых вопросах», а не в тексте требований; Цель и
Критерии приёмки не изменены.
**Режим отказа:** нет сети или поиска → **WARN** `[research: skipped — no
network]`, фаза помечается `status: "skipped"`, **score не снижается**;
меньше 5 источников Tier 1–2 после поиска → WARN с причиной и списком
найденного (не hard-fail); маркер не вставлен и не вставляется CLI (нет
секции «Источники» либо нет источника с URL) → `status: "warn"` и явная
запись в `report.md` + `run-log.jsonl` (`enriched_guarantee: "failed"`);
попытка «уточнить» Цель или Критерий приёмки ради согласования с источником →
правка отклоняется структурной защитой intent (skip/WARN) и выносится на
отдельное решение — без hard-fail всего прогона; источник без URL/даты →
запись отклоняется (WARN).

### Фаза 3 — Fact-check против репозитория

**Исполнитель:** тот же LLM-вызов, что ведёт фазу, но доказательства —
детерминированные команды репозитория (`phase: "3-factcheck"`).
**Входы:** спека после Фазы 2; рабочее дерево; git-история; `package.json`.
**Шаги:**

1. Извлечь из спеки все **проверяемые утверждения** (claims): существование
   файлов и каталогов, наличие скриптов/команд npm, состав и число тестов,
   существование спек 028–039, содержимое frontmatter (`id`, `status`,
   `commit: null`), упомянутые пути и кодовые идентификаторы, диапазоны
   строк, наличие разделов и критериев.
2. Построить таблицу `claim → тип → команда проверки → результат → действие`.
3. Проверки выполнять инструментами репозитория: `Test-Path`
   (`Select-String`, grep) для путей и строковых вхождений;
   `git log -1 --format=%H -- <path>` и `git log --oneline -n 20 -- <path>`
   для фактов истории и SHA; `npm pkg get scripts.<name>` — для скриптов;
   `node --check <file>` — для синтаксиса упомянутых скриптов.
4. Каждый claim получает результат `PASS` / `FAIL` / `UNVERIFIABLE`.
5. `FAIL` на утверждении **о репозитории** (спека описывает состояние
   репо, а репо иное) → точечная правка спеки до факта, если это не меняет
   намерение; правка фиксируется в таблице.
6. `FAIL`, снятие которого требует изменения Цели, Критериев приёмки или
   write-скоупов → hard-fail (в отчёт и Фазу 9/STOP).
7. `UNVERIFIABLE` (нет команды проверки, нет доступа) → пометка
   `UNVERIFIABLE` + запись в «Открытые вопросы»; молча пропускать нельзя.
8. Проверить, что все URL, попавшие в спеку на Фазе 2, разрешаются на этом
   прогоне; неразрешимый URL → FAIL с пометкой.

**Выход:** `<run-dir>/phase-3-factcheck.md` (полная таблица и число
`PASS/FAIL/UNVERIFIABLE`), точечные правки спеки, запись в `run-log.jsonl`.
**Критерий завершения:** каждый claim имеет результат; каждый FAIL либо
исправлен, либо помечен как hard-fail; число UNVERIFIABLE перечислено в
отчёте; таблица сохранена в артефакте.
**Режим отказа:** FAIL на утверждении о репозитории остаётся после правки →
**hard-fail** (спеку нельзя резать на ложных фактах) с STOP к капитану;
FAIL, требующий смены намерения → hard-fail; git недоступен → WARN + все
исторические claims помечаются `UNVERIFIABLE` (спеку можно продолжать,
но в отчёте это видно); правка вышла за пределы документации/edge cases →
rollback.

## Фаза 4 — делегирование CLI

### Фаза 4 — Traceability

**Исполнитель:** детерминированный CLI, без LLM.
**Делегирование:** тот же вызов CLI; секция `phase4` — связи
Цель → Критерий приёмки → Задача декомпозиции и список сирот. Собственный
обход графа скилл не выполняет.
**Выход:** раздел «Фаза 4» в `report.md` (матрица связей + сироты).
**Критерий завершения:** CLI вернул exit 0 (сирот нет) либо перечислил
сирот с id и уровнем.
**Режим отказа:** любая сирота → **hard-fail** (exit != 0); конвейер
переходит к Фазе 9 только после того, как сирота закрыта правкой,
не меняющей Цель; если закрытие сироты требует изменения Цели — **STOP** к
капитану.

## LLM-фазы (Фазы 5–10)

### Фаза 5 — Семантика

**Исполнитель:** LLM-вызов (`phase: "5-semantics"`).
**Входы:** спека после Фаз 2–3; результаты Фазы 1 (FAIL, если правка была
разрешена капитаном) и Фазы 4; baseline score.
**Шаги:**

1. Найти **противоречия** между разделами (Цель ↔ критерии, «Что делаем» ↔
   edge cases, критерии ↔ «Что НЕ трогать»).
2. Найти **дубликаты** требований и критериев: дубликат либо сливается в
   один пункт с сохранением смысла, либо обосновывается как намеренный.
3. Проверить **stale cross-refs**: ссылки на несуществующие файлы,
   разделы, id задач, спеки.
4. Найти **vague terms** («быстро», «удобно», «надёжно», «и т.п.»,
   «оптимально»): каждый либо определён числом/командой/наблюдаемым
   эффектом в спеке, либо переписан измеримо.
5. Разобрать **«Открытые вопросы»**: закрыть, если ответ уже следует из
   текста спеки; иначе оставить с пометкой «требует approve капитана».
6. Проверить, что каждый критерий приёмки измерим командой или явным
   артефактом. Критерий без проверяемого признака (`m11`) и критерий без
   verify-команды (`m13`) — дефекты класса, который конвейер НЕ правит: см.
   шаг 7.

**Выход:** `<run-dir>/phase-5-semantics.md` (противоречие/дубликат/vague
term → место → предлагаемая правка), применённые правки, запись в
`run-log.jsonl`.
**Критерий завершения:** 0 противоречий; 0 stale cross-refs; 0 vague terms
без определения; каждый дубликат слит или обоснован; каждый критерий
приёмки измерим; счётчик правок зафиксирован.
**Режим отказа:** противоречие снимается только изменением Цели или
Критериев приёмки → **STOP** (решение капитана); неразрешимая
неоднозначность формулировки → **WARN** + запись в «Открытые вопросы»;
любая правка внутри секций «## Цель» и «## Критерии приёмки» отклоняется
структурной защитой intent в CLI (см. «Структурная защита intent» ниже):
фаза получает `status: "warn"`, правка не применяется, прогон НЕ получает
hard-fail, а дефект класса `m11`/`m13` выносится на отдельное решение.

### Фаза 6 — Adversarial

**Исполнитель:** **LLM-вызов** — отдельный критик
(`phase: "6-adversarial"`). Промпт критика не содержит переписки автора
правок и его самооправданий: критик видит спеку и критерии, не историю
работы. Вызов обязательно логируется:

```json
{"phase":"6-adversarial","runner":"dsh --profile headless","model":"<critic-model>","prompt_hash":"sha256:<hex>","timestamp":"<ISO-8601>","status":"ok"}
```

**Входы:** спека после Фаз 2–5; DECISIONS/DOD как критерии качества;
критерии приёмки; результаты Фаз 1–5 (для запрета повторять уже снятые
претензии).
**Шаги:**

1. Пять независимых атак (steel-manned objections, ADVOCATUS):
   (a) completeness — чего в спеке нет для исполнения; (b) testability —
   что нельзя проверить; (c) ambiguity — что можно понять двумя способами;
   (d) scope-creep / scope-hole — что расширяет или сужает рамки;
   (e) feasibility — что невыполнимо в этом репозитории.
2. Каждый finding: `severity` (hard-fail | high | medium | low),
   `confidence` (0–1), место в спеке, `evidence`, `requiredFix`.
3. Запрещено «на всякий случай» поднимать severity: severity выводится из
   последствия, а не из настроения критика.
4. Findings с `confidence < 0.5` не выбрасываются, но помечаются и в
   repair loop идут после high-severity.

**Выход:** `<run-dir>/phase-6-adversarial.md` (таблица findings: id,
severity, confidence, location, evidence, requiredFix), запись в
`run-log.jsonl`.
**Критерий завершения:** сформулировано ≥5 атак; каждый finding имеет
severity, confidence, evidence и requiredFix; критические находки не
повторяют уже снятые Фазами 2–5; лог содержит вызов с отдельным `model`,
`prompt_hash` и `timestamp`.
**Режим отказа:** hard-fail finding → Фаза 9 (не более 3 итераций) или
**STOP**, если правка требует изменения Цели; LLM-раннер недоступен →
**WARN** `[llm: unavailable — <reason>]`, артефакт фазы не создаётся, прогон
помечается неполным, а `report.md` явно перечисляет пропущенную фазу
(фаза обязательна для закрытия спеки — капитан решает, продолжать ли).

### Фаза 7 — Simulation

**Исполнитель:** **LLM-вызов** — «агент-исполнитель без контекста»
(`phase: "7-simulation"`). Логируется той же обязательной схемой полей.

**Входы:** спека; декомпозиция; критерии приёмки; «Что НЕ трогать».
**Шаги:**

1. Пройти спеку вслух как исполнитель: «беру задачу N → что делаю →
   какой файл правлю → какой командой проверяю → что вижу».
2. На каждой задаче зафиксировать трассу: шаг, ожидаемый результат,
   фактическую опору в тексте спеки (абзац/пункт), точку блокировки.
3. Классифицировать блокировки: `blocker` (без ответа работу начать
   нельзя), `ambiguity` (можно начать, но результат будет на угад),
   `missing-verification` (нечем доказать готовность).
4. Для каждой блокировки предложить минимальную правку спеки, не
   затрагивающую Цель и Критерии приёмки.
5. Отдельно проверить edge cases спеки: воспроизводится ли каждый из них
   в конвейере (в т.ч. «research без сети», «источник противоречит спеке»,
   «oscillation repair loop», «spec gaming»).

**Выход:** `<run-dir>/phase-7-simulation.md` (трассы по задачам +
классифицированные блокировки + предложенные правки), запись в
`run-log.jsonl`.
**Критерий завершения:** каждая задача декомпозиции имеет ≥1 трассу;
каждый критерий приёмки хотя бы раз «исполнен» в симуляции; каждая
блокировка имеет класс и предложенную правку.
**Режим отказа:** симуляцию нельзя начать (нет Цели, критериев или
декомпозиции) → **hard-fail**; блокировка класса `blocker` → Фаза 9;
`ambiguity` / `missing-verification` остаются как high/medium findings;
LLM-раннер недоступен → **WARN** `[llm: unavailable — <reason>]` + фаза
помечается `skipped` в логе.

### Фаза 8 — Regeneration test

**Исполнитель:** **LLM-вызов** со слепым контекстом
(`phase: "8-regeneration"`): в промпте ТОЛЬКО текст спеки — ни плана
декомпозиции, ни findings, ни истории правок. Логируется обязательной
схемой полей; факт «только спека в промпте» фиксируется в артефакте.

**Входы:** текущий текст спеки; декомпозиция — только для сравнения
результата, не для промпта.
**Шаги:**

1. Слепая регенерация: восстановить план реализации — шаги, файлы,
   команды проверки, порядок и зависимости.
2. Сравнить регенерированный план с декомпозицией спеки: `missing`
   (задача декомпозиции не воспроизведена), `extra` (план породил
   задачу, которой в спеке нет), `mismatch` (совпала задача, разошлось
   содержание или порядок).
3. Посчитать `coverage` = доля задач декомпозиции, воспроизведённых без
   подсказок, и `precision` = доля корректных шагов плана.
4. `missing` трактуется как дефект спеки (требование не читается из
   текста), а не как ошибка регенератора: правка идёт в спеку.
5. Проверить, что регенерация не использовала write-скоупы и «Что НЕ
   трогать» как скрытую подсказку: план должен опираться на текст спеки.

**Выход:** `<run-dir>/phase-8-regeneration.md` (регенерированный план,
diff к декомпозиции, coverage/precision), запись в `run-log.jsonl`.
**Критерий завершения:** регенерация выполнена вслепую; diff
`missing/extra/mismatch` зафиксирован; `coverage ≥ 0.8`, ни один
критерий приёмки не остался `missing`; результат записан в лог.
**Режим отказа:** `coverage < 0.8` или непустой `missing` по критериям
приёмки → high-finding → Фаза 9; регенератор получил контекст вне спеки
(утечка промпта) → результат аннулируется и вызов повторяется один раз,
иначе **WARN** + пометка о недостоверности; повторный провал →
**hard-fail**.

### Фаза 9 — Repair loop

**Исполнитель:** LLM-вызов + арифметика score из CLI
(`phase: "9-repair"`). Максимум **3 итерации**, жёстко.

**Входы:** findings Фаз 5–8 с severity; текущая спека; baseline score;
снимок оригинала (`git show HEAD:<spec>` или копия из `<run-dir>` ДО правок).
**Шаги:**

1. Отсортировать findings по severity; взять минимальный набор правок,
   закрывающий максимум `hard-fail`/`high`.
2. Перед итерацией снять снимок: `<run-dir>/repair-<i>/spec.md` +
   `score-before.json`.
3. Применить правки, перезапустить CLI (`node
   .project/scripts/validate-spec.mjs <spec> --json`), получить `score_i`.
4. Сравнить с `score_{i-1}`:
   - `score_i > score_{i-1}` → итерация принята, снимок
     `<run-dir>/repair-<i>/spec-accepted.md` + `score-after.json`;
   - `score_i < score_{i-1}` → **немедленный rollback** к снимку итерации,
     итерация помечается `reverted`, правка переписывается заново (в счёт
     лимита входит);
   - `score_i == score_{i-1}` при остающихся `hard-fail`/`high` →
     **STOP (oscillation)**: дальнейшие итерации только жгут бюджет.
5. Никогда не править Цель, Критерии приёмки и write-скоупы. Правило
   продублировано структурно в CLI: правка, чей `find` пересекает секцию
   «## Цель» или «## Критерии приёмки», отклоняется ДО применения
   (см. «Структурная защита intent»), фаза получает `status: "warn"`,
   итерация помечается `intent-blocked`, дефект класса `m11`/`m13` выносится
   на отдельное решение — hard-fail всего прогона из-за него не выдаётся.
6. Остановиться досрочно, если 0 `hard-fail` и 0 `high` findings — состояние
   `clean` (спека уже идеальна: STOP без правок).

**Выход:** обновлённая спека, `<run-dir>/repair-log.jsonl` (по строке на
итерацию: `iteration`, `findings_addressed`, `score_before`, `score_after`,
`decision` ∈ `accepted|reverted|stopped|intent-blocked|no-edits`), снимки
итераций, финальный `score.json`, запись в `run-log.jsonl`.
**Критерий завершения:** любое из: (a) 0 `hard-fail` и 0 `high` — `clean`;
(b) 3 итерации исчерпаны; (c) зафиксирован STOP (oscillation). В отчёте —
score до/после, число принятых и откатанных итераций, diff.
**Режим отказа:** падение score → rollback итерации (без исключений);
отсутствие роста score → **STOP (oscillation)** с отчётом капитану;
3 итерации без достижения `clean` → **STOP** с перечнем незакрытых
findings и рекомендацией автору; правка в защищённой секции → отклонение
(skip/WARN, итерация `intent-blocked`), а НЕ hard-fail; изменение intent,
зафиксированное Фазой 10 → **hard-fail** + rollback правок Фазы 9;
CLI недоступен → STOP (нельзя проверять правки без score).

### Фаза 10 — External audit

**Исполнитель:** **ОТДЕЛЬНЫЙ LLM-вызов**, изолированный от Фазы 6:
другой runner/model ИЛИ другой промпт со свежим контекстом и без findings
Фазы 6. Тот же проход, что Фаза 6, запрещён — это и есть защита от
specification gaming. Вызов обязательно логируется отдельной записью:

```json
{"phase":"10-external-audit","runner":"dsh --profile headless","model":"<auditor-model>","prompt_hash":"sha256:<hex>","timestamp":"<ISO-8601>","status":"ok"}
```

**Входы:** оригинал спеки (версия до Фазы 2 из git или `<run-dir>`);
итоговая спека; полный diff; findings Фаз 5–8; `repair-log.jsonl`;
критерии приёмки; «Что НЕ трогать».
**Шаги:**

1. Выделить из оригинала неизменяемое ядро: Цель, Критерии приёмки,
   write-скоупы, «Что НЕ трогать», список задач декомпозиции.
2. Сравнить с итоговой версией по каждому элементу и классифицировать:
   `preserved` | `strengthened` | `weakened` | `changed` | `removed`.
3. Проверить признаки gaming: ослаблены критерии, удалены требования,
   расширены/сужены скоупы, добавлены самоподтверждающие проверки,
   формулировки переписаны так, чтобы «пройти» мех-
   проверки без изменения смысла.
4. Проверить трассируемость: каждая правка Фазы 9 должна ссылаться на
   finding Фазы 5–8; правки без источника — нарушение.
5. Вынести вердикт: `INTENT-PRESERVED` или `INTENT-CHANGED`
   (перечислить каждый изменённый элемент).

**Выход:** `<run-dir>/phase-10-audit.md` (intent diff по элементам,
признаки gaming, трассируемость, вердикт), отдельная запись в
`run-log.jsonl`.
**Критерий завершения:** проверены все 4 шага; вердикт вынесен; в логе есть
запись `phase: "10-external-audit"` с `runner`/`model`/`prompt_hash`/
`timestamp`/`status`, отличная от записи Фазы 6; вердикт внесён в
`report.md`.
**Режим отказа:** `INTENT-CHANGED` → **hard-fail** + rollback ВСЕХ правок
Фазы 9 (восстановление снимков, возврат к версии до Фазы 9) + **STOP** с
отчётом капитану; в логе нет отдельного вызова Фазы 10 → прогон
недействителен (**hard-fail**), даже если score высокий; LLM-раннер
недоступен → **WARN** `[llm: unavailable — <reason>]` + прогон помечается
неполным; аудит выполнен тем же проходом, что Фаза 6 → результат
аннулируется и помечается нарушением изоляции.

## Итоговый отчёт прогона

`<run-dir>/report.md` создаётся после последней фазы и содержит:

1. **Score до/после**: baseline (Фаза 0) и финальный score с разбивкой по
   5 измерениям и дельтой.
2. **Diff спеки**: перечень правок с фазами-источниками и diff-фрагментами.
3. **Tiered sources**: 5–10 источников Tier 1–2 (URL, tier, дата) либо
   пометка `[research: skipped — no network]`.
4. **Findings**: id, severity, confidence, фаза-источник, статус
   (`fixed` | `open` | `accepted-as-risk`).
5. **Открытые вопросы** — включая конфликты «источник ↔ спека».
6. **Лог прогона**: путь к `run-log.jsonl`, число LLM-вызовов, отдельная
   строка про Фазу 10.
7. **Вердикт прогона** и причина остановки, если был STOP.
8. Счётчики по замеченным аномалиям: WARN, hard-fail, итерации Фазы 9.

## Остановки и edge cases

- **Research без сети** → WARN `[research: skipped — no network]`, score не
  уменьшается, спека продолжает конвейер.
- **Источник противоречит спеке** → «Открытые вопросы», не правка.
- **Spec gaming** → Фаза 10: hard-fail + rollback правок Фазы 9, STOP.
- **Oscillation repair loop** → max 3 итерации; нет роста score → STOP.
- **Спека уже идеальна** → 0 hard-fail + 0 high → STOP, состояние `clean`.
- **LLM-раннер недоступен** → WARN `[llm: unavailable — <reason>]`, фаза
  `skipped`, прогон помечается неполным; детерминированные фазы всё равно
  выполняются.
- **Правки в «Что НЕ трогать»** → hard-fail + rollback.
- **Спека без блока «## Декомпозиция»** → WARN от CLI; Фазы 7, 8 сообщают
  `coverage: n/a`, вердикт не выносится.
- **Капитан не отвечает на STOP** → таймаут 30 минут, отчёт, не продолжать
  (правило STOP-точек run-spec-chain).
