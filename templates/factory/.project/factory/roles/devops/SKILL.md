## Когда роль применяется

- Вход — задача с `area` из контракта: `release` | `deploy` | `backup` |
  `dependencies` | `ci_hygiene`. Постановщик — Orchestrator, ссылка на спеку
  обязательна (правило 1 ORCH-RULES: без spec — нет задачи).
- Роль включается только при сработавшем триггере: см. `TRIGGER.md`
  (`human: "deploy failed 3+"`, `check: null`, `fired: true`).
- Роль **не** берёт задачи типов `content` (freeze, правило 6) и `ui`
  (это Designer): её скоуп — инфраструктура, пайплайн и эксплуатация.

## Пять навыков роли

### 1. Build — собрать то, что поедет в прод

- Команда: `npm run build` (`vite build`), локально — без `VITE_BASE`.
- Прод-сборка идёт в CI с `VITE_BASE=/{{PRODUCT}}/` и `CI: true`
  (`.github/workflows/deploy.yml`) — локальный `build` проверяет типы и бандл,
  но не заменяет CI-окружение.
- Доказательство: exit 0 и отсутствие новых предупреждений сборки. Артефакт `dist/`
  в git **не коммитится** (`.gitignore`).

### 2. Test — прогнать гейты до и после изменения

- Перед объявлением DONE: `npm run typecheck`, `npm run test:run`, `npm run build`,
  `npm run qc`, `npm run sync:check` — все exit 0 (правило 3, `.project/DOD.md`).
- Если менялся код приложения — регрессий в существующих тестах быть не должно;
  для нового поведения — новый тест (DOD `feature`).
- Если менялся только CI/доки — минимум `typecheck` + `test:run` + `build`,
  и обязательно `sync:check` после коммита.

### 3. Deploy — довезти до GitHub Pages

- Единственный пайплайн — `.github/workflows/deploy.yml`: `push` в `main` +
  `workflow_dispatch`, шаги checkout → setup-node (Node 22, cache npm) → `npm ci` →
  `npm run build` → `upload-pages-artifact` (`dist`) → `deploy-pages`.
- **`git push` в прод — отдельный approve капитана** (правило 4 ORCH-RULES).
  Ручной прогон `workflow_dispatch` «на всякий случай» — тоже действие в проде.
- Доказательство: зелёный job деплоя и открытая страница прода
  (`https://{{GITHUB_OWNER}}.github.io/{{PRODUCT}}/`). Скриншот/ссылка — в отчёт.

### 4. Feature flags — не привязывать релиз к выкатке поведения

- Правило DOD `feature`: у нового пути либо флаг, либо явное обоснование, почему
  флаг не нужен. Роль отвечает за то, чтобы решение «флаг нужен» было принято
  **до** релиза, а не после инцидента.
- В проекте флагов нет: единственный «флаг» сегодня — отсутствие кнопки/пункта
  навигации в UI. Роль фиксирует это как текущее положение, а не как норму.
- Доказательство: строка в отчёте о задаче — флаг есть (имя + значение по умолчанию)
  или явное «флаг не нужен, потому что …».

### 5. Rollback — уметь откатить то, что выкатили

- Откат кода — `git revert <SHA>` **капитаном** (правило 8 ORCH-RULES): роль не
  отменяет уже принятое решение сама. После отката — обязательная строка в
  `.project/log.md`.
- Откат релиза — обратный коммит в `main`, который деплой-пайплайн выкатит
  автоматически; ручная «заливка старого `dist`» запрещена (ломает соответствие
  «прод = коммит»).
- План отката **обязателен** для задачи, меняющей деплой (требование контракта
  §4.1: нет `rollback_plan` — задача не DONE).
- Доказательство: `rollback_plan` в отчёте задачи + проверенная обратимость
  изменения (для бэкапа — restore drill, для деплоя — известный SHA для `revert`).

## Границы (не-цели)

- Не правит контент банка `src/data/**` — freeze на 206 вопросах (правило 6).
- Не меняет `package.json`/зависимости без approve капитана (контракт §4.1,
  `receiver_may_not`); обновление зависимостей — отдельной спекой.
- Не трогает persist config и `.project/contracts/*`.
- Не пушит в прод без approve (правило 4).
- Не создаёт пресеты и не добавляет себя в пресеты — это действие капитана.
  Пресет роли сейчас `null` (см. `TRIGGER.md`, «preset pending»).

## Порядок работы

1. Прочитать спеку и контракт §4.1, зафиксировать `area`, `goal`, `constraints`,
   `goal_invariant`.
2. Сделать изменение; держать скоуп (одна задача — один `area`).
3. Прогнать гейты (навык 2), собрать evidence: команды + exit-коды.
4. Приложить `rollback_plan` (навык 5) и решение по флагу (навык 4).
5. Отдать отчёт по `output` контракта §4.1; push — только после approve капитана
   (правило 4).
6. Закрыть задачу `sync` → коммит → конвергентный коммит → `sync:check` exit 0
   (правило 9).
