# DOD.md — Definition of Done для задач роли DevOps

**M6.0 Phase 4 (D3) · 2026-09-28 · роль: DevOps.** Принцип фабричного DOD:
критерий без доказательства (команда + exit-код или наблюдаемый артефакт) не считается
выполненным, даже если чекбокс стоит. Этот файл **не заменяет** `.project/DOD.md` —
он уточняет его для задач `area` из `.project/factory/CONTRACTS.md` §4.1
(release / deploy / backup / dependencies / ci_hygiene).

## Общий блок (любой area)

- [ ] Задача поставлена по спеке (правило 1), `area` и `goal` зафиксированы в отчёте.
- [ ] `npm run typecheck` — exit 0 **и** `npm run test:run` — exit 0 (доказательство:
      хвост вывода + exit-код).
- [ ] `npm run build` — exit 0 (для задач, где сборка вообще задействована;
      «не задействована» должно быть сказано явно, а не подразумеваться).
- [ ] `npm run qc` — exit 0 (`Fails 0`) — банк не тронут.
- [ ] `rollback_plan` написан: что откатываем, какой командой, что видим после отката.
- [ ] Контент банка не тронут: `git diff --name-only HEAD~1 -- src/data` пусто
      (правило 6, freeze 206).
- [ ] `package.json` / `vitest.config.ts` не тронуты без approve капитана;
      `persist config` и `.project/contracts/*` не тронуты.
- [ ] Ни одного секрета: нет `.env*`, `node_modules`, `dist` в коммите.
- [ ] Один коммит задачи + конвергентный коммит; `npm run sync:check` exit 0
      (правила 3 и 9); `git push` не выполнен без approve капитана (правило 4).

## `area: release`

- [ ] Версия/состав релиза зафиксированы в отчёте (что именно уезжает).
- [ ] Гейты пройдены на том же коммите, который уезжает (не «примерно на нём»).
- [ ] Прод не тронут без approve; запись в `.project/log.md` о релизе.
- [ ] Доказательство: SHA коммита релиза + ссылка на зелёный job деплоя.

## `area: deploy`

- [ ] Изменение — только `.github/workflows/**` (или явно объяснённое исключение).
- [ ] Dry-run локально или на ветке: пайплайн не сломан (статус job виден ссылкой).
- [ ] `rollback_plan`: `git revert <SHA>` — и что делает пайплайн после откат-коммита.
- [ ] Прод не тронут без approve; `workflow_dispatch` вручную не запускается «на всякий».
- [ ] Доказательство: diff `deploy.yml` + статус job.

## `area: backup`

- [ ] Создание копии **и** проверка восстановления — оба шага выполнены.
- [ ] **Нет restore drill — нет DONE** (требование контракта §4.1: `failure_modes`).
- [ ] Что именно бэкапится — перечислено путями (`src/data/questions/**`, `.project/**`,
      конфиги), а не словами «всё».
- [ ] Доказательство: путь к копии, размер/хеш, лог drill (что восстановлено, чем сверено).
- [ ] Расписание/периодичность восстановления записаны, а не «руками когда-нибудь».

## `area: dependencies`

- [ ] Каждая находка получила одно из трёх решений: **обновить**, **принять риск
      (с записью)**, **зафиксировать в `.project/BACKLOG.md`**. «Пока не смотрели» —
      не решение.
- [ ] Обновление зависимостей — отдельной спекой (контракт §4.1: не просить
      менять `package.json` без approve).
- [ ] После обновления — все гейты заново; `lock`-файл в коммите.
- [ ] Доказательство: таблица «находка → решение → где записано».

## `area: ci_hygiene`

- [ ] Причина изменения названа наблюдаемым фактом (например: шум деплоя от
      doc-only push), а не «давно хотели».
- [ ] Изменение не ослабляет существующие гейты (если ослабляет — стоп и вопрос капитану).
- [ ] Доказательство: до/после (число прогонов пайплайна, состав триггеров,
      `paths-ignore` в diff).

## Явные стоп-сигналы (задача уходит обратно, не «дожимается»)

1. Любой гейт красный → STOP и доклад (правило 2: «автономно» ≠ «несмотря на гейты»).
2. Требуется правка `src/data/**` → STOP: контентный трек закрыт (правило 6).
3. Требуется `git push` без approve → STOP (правило 4).
4. Изменение выходит за `area` задачи → разделить задачу, не расширять скоуп.
5. `rollback_plan` не получается написать → изменение не готово к релизу.
